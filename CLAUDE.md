# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AIRec is an AI-receptionist product, split into two independent apps with no root `package.json` — always run commands from inside `frontend/` or `backend/`:

- `frontend/` — React + Vite + Tailwind SPA (**no Next.js**; migrated 2026-08-18). **The auth flow, the profile overlay and `/appointments` have UI.** The landing page and the remaining dashboard screens — `/`, `/dashboard`, `/inbox`, `/business` — are deliberately empty page grounds while they are redesigned; `/notifications` has a real empty state. The backend behind `/business` is finished and untouched by that.
- `backend/` — FastAPI service. Authentication and account profile, the business profile (services, working hours, logo) and bookings (`/appointments` CRUD, `/appointments/slots`, archive) are implemented and verified end-to-end against PostgreSQL 18. Not built: schedule overrides, a clients table, WhatsApp/assistant integration, and any test suite.

**Auth is wired end-to-end**, including refresh rotation. `login.jsx` and `signup.jsx` call `backend/`'s `/api/v1/auth/*` through `frontend/src/lib/api.js`; tokens land in `localStorage` or `sessionStorage` via `frontend/src/lib/auth.js`, depending on «Запомнить меня». `DashboardLayout` calls `useRequireAuth()`, which calls `verifySession()` — a real server round trip: `GET /auth/me` with the stored access token, and on any failure (expired, invalid, backend momentarily unreachable) a fallback `POST /auth/refresh` with the stored refresh token before giving up. Only if both fail does it clear tokens and redirect to `/login`; it renders nothing while that check is in flight, so protected content never flashes on screen. `login.jsx`/`signup.jsx` run the same `verifySession()` via `useRedirectIfAuthed()` to bounce a visitor with a live session straight to `/dashboard`. `components/ProfileMenu.jsx` holds the only sign-out control, which calls `/auth/logout` best-effort then clears local tokens regardless.

Both apps must be running for auth to work: backend on `:8000` (`uvicorn app.main:app --reload`, Postgres started first) and frontend on `:3000` (`npm run dev`). `frontend/.env.local` (gitignored) can set `VITE_API_URL`, but **is deliberately left with it commented out**: `lib/api.js` then uses the relative base `/api/v1`, which the dev-server proxy forwards to the backend. Set the variable only to reach a backend the proxy cannot — a deployed one, say. Vite only exposes keys prefixed `VITE_`, and reads them through `import.meta.env`, not `process.env`; `.env.local.example` is the template. CORS on the backend is locked to `CORS_ORIGINS` in `backend/.env` — add an origin there before calling the API from anywhere else.

## Commands

Run from `frontend/`:

- `npm install` — install dependencies
- `npm run dev` — Vite dev server on **port 3000, `strictPort`**, bound to every interface (`host: true`). The port is pinned on purpose: the backend's `CORS_ORIGINS` names it, and Vite would otherwise slide to the next free port and leave the API refusing the browser with no obvious cause.

  **To open it from a phone on the same Wi-Fi**, start both servers as usual and go to the LAN URL Vite prints as `Network:`. Nothing else is needed, and that is down to the **proxy**: `server.proxy` forwards `/api` and `/media` to `http://127.0.0.1:8000`, so the browser only ever talks to port 3000.

  That is worth keeping, because reaching the backend directly fails on three separate things and the proxy removes all of them. The backend would have to bind every interface (`--host 0.0.0.0`; it binds localhost by default). Windows Firewall would have to allow inbound 8000 — `node.exe` already has a rule from the first time Vite bound a port, Python does not, and adding one needs an administrator, which is where this actually gets stuck. And the LAN origin would have to pass CORS. Through the proxy the page and the API share an origin, so the browser has nothing to check. `CORS_ORIGIN_REGEX` in `backend/.env` still exists for the direct case; it is not used by the proxy path.
- `npm run preview` — serve the production build locally
- `npm run build` — production build
- `npm run lint` — oxlint over the whole of `src` (`.oxlintrc.json` enables the `react` + `oxc` plugins; the explicit rules are `rules-of-hooks`, `only-export-components` and `no-undef`, the last of which needs the `env` block — `browser` + `es2024` — or every `window`, `ResizeObserver` and `Intl` in the app is reported as undefined). It does not resolve imports, so a dangling relative path is not something it will catch.

Plain JSX, no TypeScript — there is no typecheck step, and no test suite exists.

Run from `backend/` (with `.venv` active, or via `.venv/Scripts/python.exe -m …`):

- `pip install -r requirements.txt` — install dependencies (versions are pinned)
- PostgreSQL 18 runs **natively, no Docker**, as the `postgresql-x64-18` Windows service the installer registers — port 5432, starts with the machine, nothing to launch by hand. The `airec` database is created once through pgAdmin; `alembic upgrade head` builds the schema.
- **Connection settings are separate `DB_*` values, not a `DATABASE_URL`** (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`). `Settings.database_url` is a computed property that assembles the asyncpg DSN and `quote_plus`-escapes the password — that escaping is the point, since a password with `@` or `/` would otherwise corrupt the DSN. Callers (`db/session.py`, `alembic/env.py`) still just read `settings.database_url`.
- An older setup put the data in a project-local `backend/.pgdata` started manually with `pg_ctl`. That directory may still exist as a leftover; it is **not** what the app uses.
- `alembic upgrade head` — apply migrations; `alembic check` fails on model/migration drift
- `uvicorn app.main:app --reload` — dev server; interactive docs at `/docs`
- `ruff check .` — lint (config lives in `pyproject.toml`, which is tooling-only — dependencies are in `requirements.txt`)

`backend/.env` is required and gitignored; copy `.env.example` and set a `SECRET_KEY` of 32+ chars or the app refuses to boot. No backend test suite yet either.

## Architecture

### Frontend stack — React + Vite, no framework

Entry chain: `index.html` → `src/main.jsx` (fonts, `globals.css`, `BrowserRouter`) → `src/App.jsx` (routes). Nothing renders on a server; the build is a static bundle in `dist/`.

Every Next.js primitive has one replacement, and mixing them back in is the thing to avoid:

| Was | Is |
| --- | --- |
| `next/link` `<Link href>` | `react-router-dom` `<Link to>` |
| `useRouter().push` / `.replace` | `useNavigate()(path)` / `(path, { replace: true })` |
| `useRouter().pathname` | `useLocation().pathname` |
| `useRouter().query` | `useSearchParams()` |
| `next/head` | `index.html` — see below |
| `_app.jsx` | `src/main.jsx` + `src/App.jsx` |
| `_document.jsx` | `index.html` |
| `getServerSideProps` | a client-side guard; there is no server |
| `process.env.NEXT_PUBLIC_*` | `import.meta.env.VITE_*` |

**The title lives in `index.html` and nowhere else** — in an SPA it survives navigation, so a per-page copy is the same string ten times over. A page that ever needs its own sets `document.title` in an effect; don't reintroduce a head-management library for it.

### Routing (`src/App.jsx`)
**There is no file-based routing.** `src/App.jsx` holds the whole route table, and every route sits inside one of two layout routes: `PublicLayout` (marketing header, no sidebar) for `/`, `/login`, `/signup`, `/forgot-password`, `/reset-password`, and `DashboardLayout` (fixed icon `Sidebar` + `Header`) for everything authenticated. Both layouts render `<Outlet/>`.

**A new route cannot be added without choosing a shell for it**, because the shell is where you nest it rather than a list you might forget to update. Files still live under `src/pages/`, but the folder is a convention now — nothing routes from it.

`*` is caught by `pages/404.jsx` inside the public shell.

- `/` — public landing page (`pages/index.jsx`). **On a phone it is a splash and on a desktop it is still empty**, and that asymmetry is deliberate rather than unfinished: below `sm` it shows the wordmark, one line of what AIRec is, «Открыть AIRec» and a «Войти или зарегистрироваться» pair, centred in the viewport; above `sm` the desktop landing is being designed separately and the phone screen is not a draft of it. The old hero (heading, paragraph, «Начать» / «Подробнее») was removed on 2026-08-19 and is in git history.
- `/dashboard` — «Главная»: empty. An analytics screen built to `design/main_page.png` — week bar chart, a 2×2 of metrics, a funnel, a category donut and a bookings table, all on invented figures since there are no aggregate endpoints — was put here and taken out again on 2026-08-21; it is in git history, charts and all (hand-written SVG, no library). Not `/` — that's the landing page.
- `/inbox` — «Диалоги»: empty. This is where the assistant's WhatsApp conversations will go; there is no channel and no message table behind it yet.
- `/appointments` — «Записи»: **built, and this is the third attempt.** Two earlier designs were each taken down whole rather than edited, so this one inherited nothing from either — v1 (a 24-hour time grid) is in commit `1e0c045`, v2 (a full-width month calendar) was archived under `src/archive/` and that folder has since been deleted; both are in git history.

  **The page is a flex row on the page element itself**, which is load-bearing: `items-stretch` measures against a *definite* height, and that is the only way the right-hand panel is genuinely full height. Wrapped in a plain div it would be as tall as its contents.

  > **`min-height` is not `height`.** A flex container whose `height` is `auto` has an *indefinite* cross size no matter how large a `min-height` clamps it to afterwards — so `flex-1` children inside it never receive a leftover to fill. Every one of them sizes to its own content instead, and `overflow-hidden` cannot save it, because that clips content; it does not cap a box that grew.

  Every other page module in this project sets `min-height` only, which is right for pages that scroll. This is the one that must not, so its page element carries a **definite `h-[calc(100vh-50px-env(safe-area-inset-bottom))] sm:h-[calc(100vh-68px)]`** — the module's own numbers, as a real height — plus `overflow-hidden`. Copy that pair, not one of them, for any other screen that has to fit the viewport.

  **The left column is three cards over the timetable; the right column is the calendar.** The left column is `justify-end`, so the grid is held to the *bottom* of it and the cards take what is left above. Pinning it down rather than letting it sit under whatever happens to be above means the hours stay where the eye last found them when a card changes height.

  **The three cards are the three questions asked with a client on the phone**, in the order they come up, each its own component under `components/appointments/`:

  - `NowCard` — who is in the chair. A countdown to the end of the booking (ticking every second, because a timer that jumps sixty at a time is a clock that has stopped), the client, the service and the span. Parallel bookings are **paged with `‹ n/m ›`**, not stacked: a business with `capacity` above one has two chairs, and two cards' worth of detail does not fit in one card.
  - `UpNextCard` — who is next. Today's not-yet-started bookings, each its own small card, sorted with `byStart` (a *total* order — two bookings can begin in the same minute, and without the id tiebreak they swap places on every render). Today only: a queue is a thing you are standing in, and Thursday is the calendar's business. The list scrolls inside the card; the row of three has one height.
  - `FreeSlotCard` — when somebody could be fitted in. The next window of at least 15 minutes, its length, and how long until it starts. A **tool, not a statistic**: the question is asked out loud, and answering it from the grid means reading a column while somebody waits.

  Each ticks on its own clock — a second for the countdown, a minute for the other two — and only while it is mounted.

  **The timetable.** `components/appointments/Timetable.jsx` draws the week or the day, and the toolbar above it steers both.

  - **The grid draws the whole day, 00:00–24:00** (`START_HOUR` / `END_HOUR`), in rows of **90 minutes** (`ROW_MINUTES`). It was 08:00–21:00 with hourly rows, and both had to change together: a booking may now be written outside opening hours, so a grid that drew only the working day could hide a booking it had just accepted — and twenty-four hourly labels down the gutter read as a ruler rather than as landmarks, where sixteen at an hour and a half are still every part of the day (1440 divides by 90 exactly, so the last row ends on midnight). `ROW_MINUTES` is only what the rows and the gutter are *drawn* in; everything positioned on the grid still comes from `rowHeight`, which stays pixels-per-hour. What the full day costs is scrolling, and it is paid once: the grid scrolls itself to **half an hour before the week's earliest opening time** on mount. The opening hour and not the current time, because the current time moves and a grid that followed it would scroll under the reader; and once per mount only, after the first real measurement, so changing the week or opening a booking never drags it back.
  - **The hour's height is measured, not chosen.** `HOURS_ON_SCREEN = 3` is the setting; a `ResizeObserver` on the scroll box divides its height (minus the sticky day-name strip) by that. A fixed pixel hour was tried at 56, 80 and 200, and every one of those answers "how tall should an hour be?" — which cannot be answered in pixels, since the same number is a cramped grid on a laptop and a wasteful one on a monitor. What *can* be answered is how much of the day should be readable without scrolling. It starts at 120 rather than 0, because everything on the grid is positioned by it and a zero collapses the rows, stacks the gutter's labels and leaves the columns blank — a grid that renders and then appears to vanish.
  - **The grid can be pulled up over the cards.** A grip strip above the toolbar toggles the page's `expanded`, and the two regions swap definite percentages — the card row `h-[35%]` → `h-0` (`aria-hidden`, not unmounted, so the three clocks keep running and nothing rebuilds), the grid `h-[65%]` → `h-full`, both on the sheet curve `cubic-bezier(0.32, 0.72, 0, 1)`. Percentages rather than `flex-1` precisely so there is a midpoint to animate. `GRID_SHARE = 0.65` is that 65% written a second time in JS, and it has to be: the measured hour is always divided out of the *collapsed* height, or raising the grid would stretch the same three hours instead of revealing more of the day.
  - The hour rows take that number **as a style, not a class**. They were `h-14` while every position was computed from the constant; the two agreed only until one of them changed.
  - **No rule across the hour.** The gutter says what time it is and the columns say which day; a line every eighty pixels across five columns was a grid drawn over a grid, and the cards on it have edges of their own.
  - **The day-name strip is grey and opaque** — `color-mix(in oklab, var(--color-ink) 7%, var(--color-surface-raised))`. Mixed rather than `bg-ink/7` because the rows scroll *underneath* these, and a translucent heading would let 15:00 show through the word "ЧТ". Today's cell is `--now` at 12% with a 2px inset top rule and its weekday in `text-now` — the same orange as the line that crosses the grid, so the column and the line say the same thing in the same voice. The corner above the gutter is deliberately not part of the strip: nothing is written there.
  - **Closed hours are hatched, not filled** (`ClosedSpan`, `HATCH`): a 135° 6/6 repeating gradient in **`--hatch`, a token with a value per theme**. It was one `ink` alpha for both and could not be: 5% ink is a grey stripe on a white page and `#0d0d0d` on a black one — a value you can measure and cannot see. The two sides do not want the same number either, since dark-on-light is read more readily than light-on-dark, so the dark theme takes the larger share (white 20% against ink 11%) to arrive at the same faintness. Faint is still the intent; faint and invisible are not the same thing. A tint says the hour is some other kind of hour; hatching says it is struck out — and it survives a booking drawn on top of it, which a fill would not. **It was briefly a flat tint when the grid went to twenty-four hours** and was put straight back: the argument for the tint was scale, since most of a full day is shut where a closed stretch used to be a fifth of the grid, and it lost to how the two actually look — struck-out reads as struck out at any size, and a tint at that scale reads as a second kind of surface rather than as an absence. A day off and a break are labelled with a dot and a word; the stretch before opening is not, because the empty grid already says it. `pointer-events-none`: the shading is information, not a wall.
  - **Every booking card is the plain `surface-card` grey.** That token exists because the two before it were both wrong here: `surface-chip` means *the chosen thing* everywhere else, and `surface-raised` at `#0e0e0e` is no fill at all on a black grid — a booking is drawn *on* something, which is the difference the token records (white / `#1c1c1c`).
  - **The status is the only colour on a card, and it is one word — not the fill.** `STATUS_TONE` maps `confirmed` → `now`, `completed` → `ok`, `no_show` → `danger`; `cancelled` falls through to the muted grey, deliberately, since it gave its hour back and already fades the card to 45% — colouring it would point at the one booking nobody has to look at. None of the three is a new hue: green already means "done" here, red "this went wrong", and `--now` orange "the present moment", which is what a live booking is. **Tinting the whole fill by status was built and taken back out**: a week of coloured blocks is a week that looks like something is happening, and it forces every other line on the card to be re-checked against three grounds — `text-ok` on a green card is 2.5:1. Two earlier answers went the same way, an automatic hue per booking of the day (`BOOKING_COLORS`, `bookingColor`) and a mark the owner picked from the closed set the API validates (`BOOKING_TINTS`, `BOOKING_TINT_MIX`); all of it is still in `lib/appointments.js`, imported by nothing. Nothing under the picker was undone — `appointments.color` keeps its stored values, and the panel omits the field rather than sending `null`, so no later save clears one; putting it back is the `PanelSelect` block noted in `BookingPopover`.
  - **What a card shows depends on how tall *and* how wide it is.** The height thresholds were always there — the name at 28px, the service at 54, the footer at 78, the status strip at 104 — and the order matters: the name first, then what they are here for, then the arithmetic. The width rule (`CARD_WIDTH`) was missing until three bookings shared one 19:00 in the week view, where a column is split between however many lanes an hour holds: at ~90px each, «Активно» came out «Актив…», the client «Nur…» and the span «19:00 –» with the price pushed off the end. Under `LABEL` (132px) the status is its coloured dot alone — the colour *is* the status, so the word is the part that can go, and it moves to `sr-only` rather than away — the price drops, the name steps 15px → 13px and the padding 10px → 8px. Under `RANGE` (108px) the footer shows `block.from` instead of `block.range`: a start is the half of a span you scan for, and a truncated end is worse than none. **The name is never dropped** — a card that cannot say who is coming has stopped being a booking, and the answer at that point is the day view, one switch away, where every card gets a fixed 240px. The width is measured, like the hour: the same `ResizeObserver` records the day column, and a block divides it by its own `lanes`. It re-runs on `days.length` too — one day and five split the same box very differently and no resize fires when only the count changes.
  - **Below that floor a cluster collapses into one card** (`GroupBlock`). `drawFor(day)` buckets a day's bookings: anything whose measured lane would fall under `CARD_WIDTH.RANGE` in the week view is gathered with the rest of its overlap chain, and `layoutDay` now hands out a `cluster` id per chain to make that possible — `lane`/`lanes` say how the column is split but not *whose company* a booking is in. The card spans the union of the group's times, wears a **dashed** edge (the one stroked thing on the grid — a booking is solid, a stack of them is not), and shows a dot per status present, «Записей: N» and the span. **It is decided on the measured lane, never on the count**: two bookings on a wide monitor are readable side by side and collapsing them there would hide what the screen had room for. The day view never groups — its lanes are a fixed 240px and it scrolls sideways instead, which is the other answer to the same question. **Clicking opens the detail the card gave up**, a left-anchored popover listing every booking whole — status, client, service, span, price — where a row opens the ordinary `BookingPopover` anchored to itself. A summary the reader cannot open is information taken away, so that panel is the price of collapsing at all. Single click in the list, not the grid's double click: on the grid the single click is being held back for selecting a booking, and inside a list there is nothing to hold it back for.
  - **In the day view a booking is a fixed 240px lane**, not a share of the column. Across five days a booking gets a fifth of the grid, which is right — the columns are the days. One day is a different problem: a single booking stretched across the screen is four short lines and a metre of empty space. What is left over is where the *second* booking at that hour goes, and past what fits the grid scrolls sideways rather than making every card narrower.
  - The week view shows **five days, Monday to Friday** (`WORK_DAYS`), slicing the *front* of `weekDays()` rather than reordering, so Monday-first still agrees with the backend's `weekday`. Two things there are easy to get wrong: the now-line's `gridColumn: 1 / days.length + 2` — grid counts **lines, not tracks** — and the weekday heading in day view, which has to be looked up by `(getDay() + 6) % 7` because `weekdayLabels()` is Monday-first and `getDay()` is Sunday-first.
  - **Stepping the week arrives from the direction of travel.** The arrows set a `direction`, and each day heading is keyed on its own date so React swaps it in one frame and the new one enters from ±12px; the booking cards under it re-key with the week and fade in on their own. **Entering only, and no `AnimatePresence`** — these are cells of a CSS grid, and a leaving heading would sit beside its replacement for the length of the animation, ten columns where there should be five.
  - **Only the grid scrolls; the page never does.** With the page's definite height the chain resolves: page → left column `flex min-h-0 flex-1 flex-col` → `Timetable` section `h-[65%]` → grid wrapper `min-h-0 flex-1 overflow-auto`. **`min-h-0` is the other half** — a flex item refuses to shrink below its content without it.
  - **The now-line has its own token, `--now` (`#ea6a1e`)** — not `danger`. Red means a cancelled booking here, and a permanent red rule across the busiest surface in the product would spend that meaning on a clock. It is **one value for both themes**, and it **shows whenever the week on screen is this week**, not whenever today is one of the five columns drawn — the line marks a time of day rather than a date, and the stricter test hid it every weekend on a Mon–Fri view.

  **The toolbar** names **the days on screen** — `dayLabel` in day view, `rangeLabel` in week view, at 17px — with a `StatusFilter` pill beside it on the left, and against the right edge `‹ ›`, a **«День» / «5 дней»** switcher and **«+ Добавить»**. It is the range and not the word «Записи», which is the page title forty pixels above it: the same label twice at two adjacent sizes is the pairing this project's type scale rules out by name, and nothing else on screen answered "which days am I looking at" in words. The heading and the filter travel together because one names what is in the grid and the other decides it, where everything on the right decides which *days* are on screen. The arrows move the **page's** `selected`, the same state the calendar is bound to, so stepping a week here moves the month over there. How far an arrow steps comes from the view through `shiftDate`.

  The bar sits **outside the grid's border, above its top rule** — the heading and the controls are what you steer the grid *with*. It carries no rule of its own: the day-name row below has one, and two lines twelve pixels apart read as a mistake.

  **The chosen segment and the add button are `surface-chip`, not `accent`.** The accent is pure white on the dark theme, and marking the current view with it put a solid white block in a black toolbar — the loudest thing on the page, for a switch that only says how many days are on screen. A switch is not an action. `surface-chip` is a step *up* from the track in either theme, which is how a segmented control has always shown its choice: the pill lifts, it does not light up.

  **`StatusFilter` filters in the client, not on the server.** `GET /appointments` takes `status=`, and using it would be a round trip for rows already in memory — ticking a box would feel like loading a page. **Nothing ticked means everything shown**, not nothing. Its four labels are translated (`booking.*`) rather than read from `BOOKING_STATES`, whose Russian labels stay there for code that has no `t` to call.

  **`BookingPopover` writes a booking and edits one — the same panel both ways.** «+ Добавить» opens it empty; **double-clicking a card on the grid** opens it filled with that booking. Two ways in need different plumbing: the button is a `Popover.Trigger` and the panel owns its own open state, while a card is a `Popover.Anchor` (no trigger listens for a double click) and the card owns it — hence `open ?? selfOpen`, with `??` and not `||`, or a controlled `false` would fall through to the internal state and the panel would never close. Double click rather than single, because a single click is what the grid will eventually spend on selecting a booking, and it is what every desktop calendar already uses to open an event.

  **On a phone it is not a popover at all — it is a sheet.** Below `sm` the same form goes into a `@radix-ui/react-dialog` rendered full-bleed and rising from the bottom edge, over the bottom bar rather than beside it (`z-[60]` against the nav's `z-50`), on the `sheet-in` / `sheet-out` keyframes and the same `cubic-bezier(0.32, 0.72, 0, 1)` at 420ms that `ProfileDialog` rides. A popover is anchored to the control that opened it, which is right on a desktop where the grid behind is *why* you know which day you are writing for; on a 390pt screen there is no grid behind — the calendar is the screen — and a 400px card floating in the middle of it is a desktop shape in a phone's clothes.

  It runs **from the bottom edge up to `calc(12px + env(safe-area-inset-top))`**, top two corners rounded. It was `h-[90dvh]`, which is a proportion rather than a place — on a tall phone that left a band of page with nothing in it, on a short one it ate the form. Defined by where it *stops* instead: twelve pixels clear of the status bar, enough for the radius to be seen and to leave somewhere to tap out, and no more. The inset is added rather than assumed — 0 in a browser tab, where the status bar is the browser's own chrome and outside the viewport already; the notch's height once this is installed.

  **The top bar is the controls and also the handle.** Close on the left, the title centred, save on the right — three fixed positions a thumb learns once, with the actions at the edges where a hand already is. The bar takes the form's own `px-6` so the buttons' outer edges line up with the edge of the fields, which is the thing below them the eye measures against, and **both** ends carry a filled circle: the close is `ink/8` where the save is `surface-chip`, a step quieter because it is the way out rather than the thing to press, and an ink tint rather than a surface token because it has to show on a sheet that is white on one theme and black on the other; the form's own «Отмена»/«Сохранить» are `isDesktop`-only for that reason, since the same two decisions said twice on one screen is a screen asking the same question at both ends. «Сохранить» reaches the form through `form={formId}` (a `useId`, because several of these mount at once behind the grid's cards) — it is a sibling of the form, not a child. Delete stays at the foot in both shells: it is not one of those two, it is the third thing.

  **Dragging that bar down dismisses the sheet** — pointer events and an inline transform, not a drag library, because Motion would bring `AnimatePresence` and `forceMount` with it and that is a different animation scheme from the one every other panel here rides. Two details are load-bearing: the grip is the *bar* and not the sheet, since the form under it scrolls and a sheet that drags from its body closes when somebody meant to reach the phone field; and a press landing on one of the bar's buttons returns early, because capturing the pointer for the whole row would end the press somewhere the button never sees and swallow the tap. Past 120px it closes, under it it springs back, and the transition is on only while nothing is held so the follow stays exact.

  Three things that split makes load-bearing. **The two shells are different primitives, so the breakpoint has to be a value** — `useMediaQuery('(min-width: 640px)')`, the case `lib/media.js` exists for — and the form between them is built once into a `body` variable, because writing it twice is writing two forms that agree until one is edited. **Both `Popover.Close` buttons became plain buttons** calling `setOpen(false)`, since a primitive's own Close only speaks to the primitive it belongs to. And Radix names a dialog from its `Title`, which the visible heading cannot be — that element also renders inside a popover, where `Dialog.Title` would throw — so the sheet carries an `sr-only` title of its own.

  **On a desktop it is a popover, not a modal**, anchored to the left of the «Добавить» button (`side="left"`, `align="center"`) with no scrim. The two are not interchangeable: a modal dims the page and takes it away, which is right for a form you went into on purpose and wrong for adding a booking, where the grid behind is the reason you know which day and hour you want. `collisionPadding` gives the top **80px** — the 68px header plus the usual 12 — because the panel is `z-[60]` and the header `z-40`, so nothing else stops it painting over the page title. **The height cap needs a fallback and it is load-bearing**: `max-h-[var(--radix-popover-content-available-height,calc(100vh_-_92px))]`. Radix writes that variable only after it has measured, so on the frame the panel first paints it does not exist — and an unset variable inside an arbitrary value makes the whole declaration invalid, which is no cap at all. Uncapped, a seven-field form is taller than the window, and the positioner then places a box it cannot fit: the top goes off screen and takes the heading with it. It renders from `Timetable`, not from the page: Radix positions and traps focus against the element that opened it, so a trigger and its popover cannot live in different components.

  **Every panel on this screen arrives the same way**, through `components/appointments/panel.js`. Four popovers open here — the booking form, the month, the service list and the status filter — and a screen where each appears differently is a screen where none of them is *the* way a panel arrives. `PANEL_MOTION` is that one string: the `popover-in` / `popover-out` keyframes from `globals.css`, scaled from `--radix-popover-content-transform-origin` so each grows out of the control that opened it, plus `motion-reduce:animate-none`. Radix mounts and unmounts its content, so both halves have to be animations rather than transitions — there is no previous value to transition from, and without the closing one a panel blinks out.

  Its fields, and why each is what it is:

  - **Date** — `DateField`, on a full-width line of its own. It shared the start row with a clock and a label, where three controls on a 400px row squeezed it down to its calendar glyph — a date field that could not say what date it held. `DateField` is a popover holding the same `MonthCalendar` the panel beside it uses. It was a native `<input type="date">`, whose calendar the *browser* draws: a white sheet with a blue selection, in a product that has no blue. Not a second calendar written to look like the first, either — two implementations of "which day is today" agree until one of them is edited. Choosing a day closes it, and moving it moves the page's `selected` with it, or a booking written for Thursday from a screen showing Monday would not appear anywhere.
  - **Service** — `ServiceField`, a combobox: type it, or open the price list and pick one. **Both, not either.** A day contains things a business sells once, and making the list the only way in would mean inventing a permanent service to record a single afternoon. The list filters as you type. Typing a name unhooks the chosen row (`service_id` → null) because it is no longer that service; changing the *price* does not, because a different amount for the same service is a discount.
  - **Price** — a digits-only field with a `₸` suffix. No thousands separators while typing: a field that reformats under the caret is a field that moves the caret.
  - **Time** — two `TimeField`s on **one row**, start and end sharing it evenly with an em dash between them, **typed rather than picked**. Evenly because the pair is one span and neither end of it outranks the other; the old fixed 86px was sized against the date that used to sit beside it. There is no end *date* on purpose — a booking past midnight is an end clock earlier than its start, and the arithmetic wraps. `1430` becomes `14:30`; the two halves are padded in opposite directions (a lone `9` is nine o'clock, a lone `3` after the hour is half past), and out-of-range values are clamped rather than refused. A menu of every quarter hour was a list rather than a clock; a native `<input type="time">` drops the browser's own sheet; a hand-built pair of scrolling columns fixed the colours and kept the wrong idea. The end follows the service's length until it is moved by hand, and travels to the API as `duration_minutes`.
  - **Status** — an `@radix-ui/react-select` row, because it answers a small closed set, and **only when editing**: a booking being written down has not happened yet and none of the four states is a thing anyone can say about it. A colour picker sat beside it and has been taken out — see the grid's card-fill note for what survived. **The trigger wears `FIELD`**, the same ring every other control on the panel has: bare text with a chevron is the shape «Настройки» uses, where hairlines between rows are what make each one a row, and dropped among seven bordered fields it read as a caption rather than as something pressable. **The label is inside the field on the left and the answer sits against its right edge** — a select always has a value, so there is no empty state a placeholder could fill, and the label has to stay visible beside its answer. Outside the field it needed a column of its own, which made this the only row on the panel that was not simply a field the full width of it.
  - The form reads as **three blocks, not eight rows**: `Group` takes an `apart` flag that swaps its 12px gap for 24, and it is set after the price and after the times — the two boundaries where the subject actually changes (what is being sold, when it happens, who it is for). A reader then finds a field by remembering which block it was in rather than by counting down the column. One class or the other through a ternary, never `mb-3 mb-6` in one string: two utilities of the same property are resolved by stylesheet order, not by the order they are written.
  - Client name, phone and note are ordinary fields, and they come **last** — they are the part nobody has to fill in, and putting them first makes a short form look long.
  - **Delete is in the button row, and takes two presses.** It is not a status change: cancelling keeps the row because that is what the owner looks back on, while `DELETE` is for a booking that should never have existed. The second press is the confirmation — a dialog inside a popover is a layer on a layer for a two-word question, and one red button beside Save is one slip away from losing somebody's afternoon.

  The panel is capped at 560px and scrolls inside itself, and the two blocks that grow with the business — the price list and the times — have ceilings of their own, so a long price list cannot push the client's name off the bottom. **Adding, everything starts blank**, the date included: seeding the one service a new business happens to have was a value nobody entered, and a price that had not been agreed is the kind of default that gets saved by accident. Editing, every field is filled from the booking — a PATCH says the same things a POST can, which is why `UpdateAppointmentRequest` grew `service_name`, `price` and `duration_minutes`.

  **The calendar lives in the right panel** (`aside`, `xl:w-[calc(300px+2rem)]` — the calendar's own 300px plus its `p-4`, written as the sum so the two cannot drift). Beside the timetable it was a card sitting above thirteen hours of grid, taking height the one scrolling thing on the page had to give up. The panel is flush rather than rounded — a hairline and no box — for the same reason the timetable is: a card with a radius cannot be 100% of anything without margins to float in.

  `MonthCalendar` **is not a card**: no radius, no fill, no border, no padding of its own. Its sizes come from this app rather than from the drawing it was measured against — **every square control on this page is 36px** (a rail item, a header icon, the toolbar's arrows) and **the timetable's dates are 13px**, so a day cell is one of those squares with one of those dates in it. Today is `surface-chip` and semibold — a real value in both themes, where the `ink/8` it used to be was a grey one step off a black page and one step off a white one. The selected day is **`--now`**, the same orange as the now-line and today's column, so on the common day all three agree. Weekends are dimmed to the same grey as days outside the month. The grid is always **42 cells / six rows** (`monthGrid`), so the card does not change height four times a year.

  **Two motions on it, both directional.** Stepping a month cross-slides the grid the way it was stepped (`AnimatePresence mode="wait"`, keyed on `monthIndex`, ±14px), and the orange selection **travels** between cells on a shared `layoutId` and a spring, the sidebar marker's trick — a month reads as one selection changing place rather than two cells changing colour. The `layoutId` is **per instance**: `MonthCalendar` renders twice on this page (the right panel and the date field), and one shared id would fly the marker from one calendar to the other whenever both were mounted.

  **`ChatFeed` fills the room under the month.** The panel is the page's full height and the calendar a fixed 300px card at the top of it, so everything below was empty on the one screen the owner is already looking at. A feed is the right shape for that space — it has no height of its own to insist on, so it takes the leftover (`min-h-0 flex-1`) and scrolls inside itself. Chats rather than more bookings: the three cards over the timetable already answer everything the calendar can, and none of them answers the other half of the day — somebody is messaging *now* and has not been dealt with, which is invisible until you leave for «Диалоги».

  **There is no backend behind it.** `/inbox` has no channel and no message table, so the page currently hands it `DEMO_CHATS` — **three invented rows in a block marked to be deleted**, there so the layout can be looked at and argued with. Handing it `null` instead draws the honest empty state a new account would see. Keep that block marked and keep it temporary: an analytics screen built on made-up figures went onto `/dashboard` and came back off whole for exactly that reason. The row is built and waiting: a chat is `{ id, at, client, preview, state }`, it wears **`surface-card`** and not `surface-raised` (both are edgeless fills, but `#0e0e0e` is a step off a page and no step at all off the pure black this panel sits on), the time is the loudest thing on it as in the reference, and `CHAT_TONE` spends colour the way the grid's `STATUS_TONE` does — `waiting` is `--now` because somebody is on the other end at this moment, `new` is `ok`, and an answered chat is muted because it is the ordinary case.

  It is `hidden xl:flex`, and the component deliberately sets no `display` of its own so the caller's `hidden` is not fighting a baked-in `flex`. Below `xl` the three regions stack and the page still does not scroll, so the calendar already ends up below the fold and anything added under it makes that worse. That is a small-screen layout still to be designed, not a scrollbar to add back.

  **On a phone the screen is a calendar and nothing else.** `MonthScroller` replaces all of it below `sm`: the left column and the right panel are `hidden sm:flex`, and it is `sm:hidden`. The three cards, the timetable and the chat feed are each built for a screen you can put two columns on, and stacked into 390 points they were six regions arguing over one viewport that is not allowed to scroll. Hidden rather than unmounted, as `/profile`'s header is — a component torn down and rebuilt at 640px is one whose clocks restart and whose scroll position is lost every time the window is dragged. The cost is that a desktop still builds the scroller's DOM behind `display: none`; that is 546 cells created once, and the alternative is a `useMediaQuery` where a class already answers.

  `MonthScroller` is **a different control from `MonthCalendar`, not a wider one**. That one is a 300px card with two arrows, which is right beside a timetable — a picker next to the thing it steers. Here the calendar *is* the screen, and a picker showing one month at a time makes "is the 3rd of next month free" into two taps and a wait. So the months are laid end to end and scrolled through, each month's name sticky over its own weeks. **A year, not an infinite list** (`MONTHS_BACK` 1, `MONTHS_FORWARD` 11): an endless one needs windowing to stay cheap, and 13 months of 42 cells renders in one frame without any of that. It opens on the month in play through `scrollIntoView` — once, guarded by a ref rather than an empty dependency list, since `months` is a fresh array every render — and instantly, so tapping a day in December never hauls the list back to August.

  **The month's name is said twice, at two sizes, and the big one does not travel.** A fixed 28px heading above the grid answers "where am I" and *changes* as a new month reaches the top; 17px headings in the flow answer "where does the next one begin". Two steps apart, as the type scale requires. Each month used to carry its own `sticky` heading instead, so an arriving month pushed the departing one up and off screen — motion that says "this label is leaving" about a label that is not going anywhere. Which month is at the top is read from `offsetTop` against `scrollTop` on scroll, not from an `IntersectionObserver`: with two months visible both are on screen, and the question is which one the top edge is inside. The first month in the run has no small heading (no boundary above it to mark) and the weekday letters are **one row for the whole calendar**, not one per month.

  **`CONTROLS_HEIGHT` is reserved above it** — `calc(96px + env(safe-area-inset-top))`, and it lives in `grid.js` because three screens have to agree on it: the calendar reserves it, `MobileToolbar` fills it, `MobileSearch` puts its field in the same place. **The bar carries that height itself rather than filling its parent.** It was `h-full`, which is right inside the calendar's reserved box and wrong everywhere else — on the day screen the parent is the whole screen, so the bar took all of it and `items-end` pushed the row to the bottom with the grid shoved off below. It began as the desktop header's 68, which is the wrong measure: that is one row of small controls on a wide bar, where this has to hold a row sized for thumbs (44pt is the floor) with air around it. The inset is added rather than baked in — 0 in a browser tab, the notch once this is installed to a home screen, the same reason the bottom bar carries the inset for the home indicator. Reserved so that controls landing there do not push a year of months down on the frame they mount. **`MonthScroller` owns the room and the caller owns what fills it** — it takes a `controls` node, because the page has the services, the week and the zone those controls need while the calendar only knows about months.

  **`MobileToolbar` is what goes in it**: three round buttons in one `surface-card` pill against the right edge — filter, search, «+» — the shape the reference uses and the third of the screen a thumb already reaches. The order runs least to most consequential, so the one that changes the day's record is furthest from an accidental tap on the way to the others. **«+» and search are wired**; the filter has nothing to filter until the calendar carries markers, so it is placed rather than invented.

  **Search comes down over the calendar from the top edge** (`MobileSearch`): a field in the same reserved bar plus a list of results, with the × in that bar the one way back. It slides in from `-100%` on the sheet's own curve and leaves the way it came — arriving from the indicators says the field came from the top of the phone, which is where the bar it lands in already was. **Over rather than instead**: the calendar stays mounted underneath, so it keeps its scroll position and a year of months is not rebuilt for a search somebody may close a second later; the panel is opaque `bg-ground` so those months are not scrolling behind a list that has nothing to do with them. `m` needs no `LazyMotion` of its own here — `PageTransition` wraps every page in one. It reads `GET /appointments?query=` with **no date range**, which the backend deliberately treats as "the whole history" — looking for a client means looking for every visit they ever made, not the ones inside whichever month is on screen. Debounced at 300ms and held until two characters, because a search across the history is a real query and «Айг» on the way to «Айгерим» is three requests nobody was going to read. Its four states each say a different thing, and the first — nothing typed — says what this searches rather than that it found nothing. A result leads with the **date**, since a booking pulled from anywhere in the history has no position to say when it is, and tapping one opens the ordinary editor anchored to the row.

  That search is also why `STATUS_TONE` moved out of `Timetable` and into `lib/appointments.js` as **`statusTone(status)`**, beside `statusLabel`: two screens read it now, and two copies of a three-line map are two maps that agree until one is restyled. The buttons carry their real labels rather than placeholder ones, and `ToolButton` spreads every prop onto its `<button>` — Radix's `asChild` hands the trigger a ref, and React 19 passes that as an ordinary prop, so no `forwardRef` is needed but a component that swallowed props would never open anything.

  **The scroll box is `relative`, and that is load-bearing**: `offsetTop` is measured from the nearest *positioned* ancestor, not the nearest scrolling one, so without it every block was reported against something further up the page and the heading named the month *before* the one on screen — an error exactly the height of everything above the grid.

  Days from the neighbouring months are drawn as **blank space rather than dimmed numbers**, because in a stacked run the 1st of September would otherwise appear twice, once at the foot of August and once at its own head. The marks are the desktop calendar's — `--now` for the day in play, `surface-chip` for today — but as a filled circle rather than a change of text colour: a phone is read at arm's length and in sunlight, where two greys are one grey.

  **The days carry no markers yet**, and that is not an oversight: the page fetches one week of bookings at a time, so dots would appear on seven days and nowhere else, which reads as broken rather than as empty. They arrive with a wider fetch.

  **Tapping a day opens `MobileDay`**, which arrives from the right the way a drill-down does — a month says which days exist, a day says what is in one of them. It carries the same `MobileToolbar` with a back button passed as `leading`, the week the day sits in as a strip (so Friday is one tap rather than a trip back to the calendar), the date in words, and then the hours with the bookings on them. Over the calendar rather than instead of it, so a year of months is not rebuilt because somebody looked at Thursday.

  It is **its own component rather than `Timetable` made narrow**: that one carries a status filter, arrows, a day/week switcher, an add button, a grip that pulls the grid over three cards, day-name columns and a five-day lane layout — every one an answer to having a wide screen, and a "hide all of that" prop would leave one component holding two designs. What the two genuinely share is arithmetic, and that already lives in `lib` (`layoutDay`, `closedRanges`, `byStart`, `statusTone`) and now in **`components/appointments/grid.js`** — the window (`START_HOUR`/`END_HOUR`/`WINDOW_FROM`/`WINDOW_TO`) and `HATCH`, moved out of `Timetable` so the second screen could not copy them. **A lane is a third of the column** (`VISIBLE_LANES = 3`), not a share of it. A booking used to take the whole width when it was alone and a fraction when it was not, so one booking was a card the width of the phone holding four short lines while three were 110px each — too narrow to read a name in. A fixed third fixes both ends, and past three the grid **scrolls sideways** rather than dividing further, which is the same answer the desktop day view gives. The lane width is measured in a `useLayoutEffect` — everything in the column is placed from it, so measuring after the paint would give one frame with every card stacked on the last. `laneCount - 1` vertical rules run the full height between lanes, because two cards 8px apart read as one wide card with a seam. The gutter is `sticky left-0`, unlike the desktop's, which may scroll away on a screen wide enough to hold the day; here losing it means reading a card with no idea what hour it is in. **On a day that scrolls sideways the swipe gives up the horizontal axis** — one gesture cannot mean two things.

  Closed stretches carry the desktop's rule as well as its hatch: **a day off and a break are named, the hours before opening are not** — the first two are facts about the business and the hatch alone leaves you guessing which of them a shaded band is, where the stretch before 10:00 is simply outside the day and the empty grid already says so. Two things it deliberately does differently: **hourly rows** (the desktop's 90 minutes exist because sixteen labels beside five columns are landmarks where twenty-four are a ruler; with one column and a screen that scrolls, the hour is the unit anybody names a time in) and **a rule on every hour** (the desktop draws none because a line across five columns is a grid over a grid). It opens on the current hour on today and half an hour before opening on any other day, once per day shown. **The now-line carries the clock**, as a filled `--now` pill in the gutter rather than a dot on the grid: the line says where now is and leaves you to work it out from the two hour labels it sits between, where the pill says it outright — and the gutter is the column times are written in, so on the grid it would be a label floating over whatever booking was behind it. Filled because it sits over the hour label nearest it and one of the two sets of digits has to be plainly on top; `text-white` rather than `text-surface`, since `--now` is a real colour in both themes.

  **Swiping it sideways steps a day**, and the gesture has to be told apart from a scroll before it can be answered: the first 8px decide which axis this press belongs to, and once it is the vertical one the swipe is abandoned for the rest of that press — deciding once rather than continuously is what stops a diagonal drag flipping between scrolling and stepping. `touch-pan-y` on the box is the other half: without it the browser owns the horizontal pan and the pointer events arrive already cancelled. Past 60px it steps in the direction the finger went, and the arriving grid enters from that side — keyed on the day and **entering only**, since a leaving grid would sit beside its replacement for the length of the animation, two days of hours in one column. Tapping a date in the strip clears the direction first, so a day picked there simply appears.

  **What is still missing:** archiving. `PATCH {"archived": true}` is finished on the backend and nothing in the UI sends it, and the right panel still holds only the calendar — there is no read-only booking-detail view, since the editor doubles as one.

- `/business` — «Бизнес»: **also empty, for the same reason.** Its first version — a 30/70 identity card, a price list and a working-week table, all under `components/business/` — was removed on 2026-08-19 and is in git history.

  What survived, and is the point: **the data layer stays in `src/lib`.** `api.js` keeps every booking and business endpoint, and `appointments.js`, `dates.js`, `cities.js`, `businessOptions.js` and `schedule.js` keep the rules underneath the screens. A screen is what keeps being redrawn; the arithmetic below it is what the next version starts from — and `/appointments` proved it, since rebuilding that screen was mostly a matter of importing modules that had been sitting there unused. `cities.js` and `businessOptions.js` are still imported by nothing and tree-shaken out of the build; the other three are in use.

  The **route stays registered**, rendering a bare page ground, because the sidebar has a «Бизнес» item and an empty page is an honest answer where a 404 is not.

  Removing those screens took `cmdk`, `@radix-ui/react-popover` and `@radix-ui/react-switch` with them — nothing else imported any of the three. **`@radix-ui/react-popover` came back on 2026-08-24** for the booking panel, the date field and the service combobox; `cmdk` and the switch are still gone, and the reasoning for choosing them is under **Styling convention**.

  **The business backend is finished and untouched by any of this** — see **The business behind an account** below.
- `/profile` — the account **as a screen, for phones**. The bottom bar's fifth slot points here; the desktop rail opens a popup instead and never links to it. Not hidden on a desktop, just not linked — see "Profile overlay" below for why there are two shapes.
- `/login` and `/signup` — **laid out from `vercel.com/login`**, measured rather than eyeballed: a 360px centred column, a 32px heading at `-0.04em` tracking, 40px controls, 16px text with 12px of horizontal padding and a 6px radius, 10px between fields. **`components/controls.js` holds every one of those values** — `CONTROL`, `FIELD`, `FIELD_ERROR`, `BUTTON_PRIMARY`, `BUTTON_SECONDARY` — so the pages are twins structurally rather than by anyone remembering to keep them so. `/forgot-password` and `/reset-password` read from it too, and `OtpInput`'s six boxes wear the same three-step ring, so all four auth screens are one surface.
- `/login` and `/signup` — built, intentionally near-identical: no `<label>`s (inputs use `placeholder` only); password field has a show/hide toggle (local `showPassword` state flips the `input type` between `password`/`text`); a `<hr>` sits below the submit button, followed by "Continue with Google" / "Continue with Apple" buttons (`public/google_logo.svg`, `public/apple_logo.svg`) — **UI only, not wired to real OAuth**; a bottom line cross-links to the other page (`Log In` / `Sign Up` in accent blue `#3248F2`). `login.jsx` also has a row the signup page has no counterpart for — a «Запомнить меня» checkbox on the left and the "Forgot password?" link on the right, paired onto one line because the link already sat alone there and the checkbox carries the same weight. It's a **native `<input type="checkbox">` with `appearance-none`**, not a Radix one: space-to-toggle, form semantics and focus are already right, and Radix is for behaviour that is hard, never for looks. Both controls carry `py-2.5 -my-2.5`, which grows the tap target to 38px while the negative margin keeps the row 18px in the layout. `login.jsx` also shows a green success banner when `?reset=success` is in the URL. Keep the two pages in sync when restyling one — they're meant to stay visual twins. Both submit to the backend (see the auth-wiring note above) and show inline errors — `login.jsx` a single message above the `<hr>`, `signup.jsx` per-field messages (from 422 `fields`) plus the same general-error line for 409s/network failures. Every text input across `login.jsx`/`signup.jsx`/`forgot-password.jsx`/`reset-password.jsx` blocks whitespace client-side (a `/\s/.test(value)` check turns the border red with a "No spaces allowed." message) — the backend also rejects it, this is just an earlier signal. All four forms set `noValidate` on the `<form>` so the browser's native validation bubble (e.g. Chrome's built-in "must contain @" tooltip on `type="email"`) never appears — every message shown is ours.
- `/forgot-password` — email-only form; posts to `/auth/forgot-password` then pushes to `/reset-password?email=<email>` regardless of whether the address is registered (the backend response is deliberately identical either way).
- `/reset-password` — the six-digit code screen. Reads `?email=` with `useSearchParams` and returns `<Navigate to="/forgot-password" replace/>` when it is missing. The code itself is entered via `components/OtpInput.jsx` — six boxes with auto-advance, backspace-to-previous-box, and paste-fill, shared with the profile's email-change step. A wrong code clears the boxes and shows a red message; "Resend code" re-calls `/auth/forgot-password` with a 30s client-side cooldown. On success it redirects to `/login?reset=success`.

### API client (`src/lib/`)
- `lib/api.js` — the only place that calls the backend. One `request()` helper does the `fetch`, resolves the API base (see `.env.local` above), and throws `ApiError` (`.code`, `.message`, `.fields`, `.status`) on any non-2xx or network failure, parsed straight from the backend's `{error: {...}}` envelope. Add new endpoints as small named exports here (`register`, `login`, `refresh`, `logout`, `me`, `checkUsernameAvailability`, `forgotPassword`, `resetPassword`, `updateProfile`, `requestEmailChange`, `confirmEmailChange`, `cancelEmailChange`, `getPendingEmailChange`, `requestPasswordChange`, `confirmPasswordChange`, `listSessions`, `revokeSession`, `revokeOtherSessions`, `deleteAccount`, `restoreAccount`, `getBusiness`, `updateBusiness`, `uploadBusinessLogo`, `deleteBusinessLogo`, `getServices`, `saveServices`, `getWorkingHours`, `saveWorkingHours`, `listAppointments`, `getSlots`, `createAppointment`, `updateAppointment`, `deleteAppointment`, `uploadAvatar`, `deleteAvatar`) rather than calling `fetch` from a page. **Every request carries a 10s `AbortSignal.timeout`.** Without one, a host that is reachable but has nothing listening on the port — a phone pointed at a laptop whose backend is bound to localhost — leaves `fetch` unresolved until the OS TCP timeout, a minute or more, during which the form shows «Входим…» and nothing else. A timeout turns that into a `timeout` `ApiError` the user can read. Three details worth knowing: `request()` takes `formData` instead of `body` for uploads and deliberately omits `Content-Type` in that case — the browser must set its own multipart boundary. And `mediaUrl()` exists because uploaded files are served from the backend *root* (`/media/...`), not under the `/api/v1` prefix that `VITE_API_URL` points at, so `user.avatar_url` has to be resolved through it before use in an `<img src>`.
- **`lib/viewState.js` is what a screen remembers when you leave it.** Every route change unmounts its page — `PageTransition` swaps the outlet — so state is rebuilt each time a screen is opened, which is right for a form and wrong for a view: a click on «Диалоги» and back put `/appointments` on today, in the week view, grid lowered, any open day closed, however carefully all four had just been set. `useRemembered(key, initial)` is a `useState` that survives that, backed by a **module-level `Map`, not `sessionStorage`** — this is view state rather than a preference, so it is worth keeping across a click on the navigation and worth losing on a reload, and a `Map` stores a `Date` or a `Set` as itself where storage would need a serialiser for each. Keys are `screen.thing`, like the translation keys and for the same reason. `/appointments` remembers the day, the view, the status filter, whether the grid is raised and whether the phone has a day open; **the search deliberately is not** — a search is something you were doing rather than somewhere you were. `clearTokens` calls `forgetView()`, which is the one place every end of a session passes through: without it the next person to sign in on a shared machine opens somebody else's Thursday.
- **`authed(call)` in `lib/auth.js` is how every data request is made.** The access token lives fifteen minutes and nothing was renewing it: `verifySession()` runs when the dashboard shell mounts and on every route change, which covers arriving at a page and covers nothing after that — leave a screen open through lunch and the next request comes back «Access token is invalid or expired.» with a live session sitting in storage behind it. `authed` runs the call, and on the *one* error that means "this token specifically" (`not_authenticated`) renews and tries again.

  **It renews through `verifySession()` rather than calling `refresh()` itself, and that is the load-bearing part.** A page makes several of these at once, so several hit the wall in the same instant; `verifySession()` is single-flight, so they share one renewal. Calling `refresh()` from each would send the same refresh token three times, and a replayed refresh token is treated as theft and revokes every session the user has. The grace window on the server forgives that, but a client that needs forgiving is a client waiting to be caught out.

  Nothing outside `lib/auth.js` calls `getAccessToken()` any more — 22 call sites went through this on 2026-08-24. Write new endpoints as `authed(fn)` or `authed((token) => fn(token, ...))`.
- `lib/auth.js` — token storage across **both** `localStorage` and `sessionStorage` (`saveTokens`, `getAccessToken`, `getRefreshToken`, `clearTokens`) — see «Запомнить меня» below, `verifySession()` (the real check: `me()`, falling back to `refresh()` and re-saving tokens on success, clearing them and returning `null` if both fail), and two hooks built on it: `useRequireAuth()` (used by `DashboardLayout`, redirects to `/login` and returns `null` until a session is confirmed — callers must not render children until it returns a user; it returns the **user object**, not a boolean, so the shell can render their avatar without a second `/auth/me` call) and `useRedirectIfAuthed()` (used by `login.jsx`/`signup.jsx`, bounces a visitor with a live session to `/dashboard`). Reach for `verifySession()` anywhere the answer has to be correct — a token being present is not the same as a session being live.

### Dashboard shell

**Two shapes, one set of destinations.** `components/navigation.js` holds the four routes; the rail and the bottom bar both read it, so a screen added there appears in both rather than being reachable on a laptop and invisible on a phone. The `env()` is the iPhone home indicator; leaving it out of any one of the three puts a scrollbar on every page.

Pinned at the bottom, separate from that array, is the profile avatar — a **toggle button, not a link**: it opens `ProfileMenu`. `DashboardLayout` passes the whole `user` down (plus an `onUserChange` setter) so the rail avatar, the popup, and the settings dialog all share one fetched user.

### Profile overlay — no routes involved
The profile area is **an overlay on a desktop and a screen on a phone**, and both read the same `PROFILE_SECTIONS`.

Why two shapes: the popup hangs off the rail's avatar button, which is exactly right when there is a rail — it comes from the control that opened it and leaves the page behind visible. Below `sm` there is no rail to hang off, and a 264px panel floating over a 390pt viewport is a desktop shape in a phone's clothes. `pages/profile.jsx` is the phone's answer: an **ordinary route** with the usual cross-fade and the bottom bar still under it, so leaving is a tap on any of the other four. It drops only the header — on a phone that bar carries the app's name and a bell, and neither belongs above a screen about you — which `DashboardLayout` does by passing `Header` a `hidden sm:flex` class on that path.

**The sections it opens are what behave differently.** `ProfileDialog` is a centred panel that fades and scales on a desktop, and on a phone a **full-bleed sheet rising from the bottom edge**, over the navigation rather than beside it — those are forms you went into on purpose, and a sideways tap out of one is not a way out worth offering. The × in its header is the way back. Which animation runs is a *value*, not a class, so it comes from `useMediaQuery('(min-width: 640px)')` in `lib/media.js` — reach for a `sm:` class first and come there only when a prop has to change.

Its curve is **`cubic-bezier(0.32, 0.72, 0, 1)` at 420ms**, the one iOS uses for its own sheets, and springs were tried and rejected at both ends: a soft one read as sluggish, since over a whole screen height the tail of a slow settle is time spent waiting, and a stiff one read as rigid, since a spring starts at maximum acceleration and that is what the eye calls abrupt. A system-style **stacking effect** — the shell scaling back to 0.93 behind the sheet, over a dark ground — was built on top of this and taken out again; it is in git history. If it is ever wanted back, the load-bearing detail is that it must be a *conditional class* and not a Motion value: any non-`none` transform makes an element the containing block for its `position: fixed` descendants, and the bottom bar is one.

Its layout comes from `design/profile_example.png`: identity centred — avatar with an edit badge, name, and **the email under the name rather than as a row**, since it identifies the account instead of leading anywhere and a row whose only job is to be read is a row you keep tapping by mistake. Then **one card**, every section a row inside it, divided by hairlines that start after the icon column so the icons read as a single strip down the block instead of being chopped by every line. The reference sorts its rows into named groups; four rows with short labels and distinct icons did not need it, and the headings ended up naming groups you could already see. Rows carry a value on the right where they have one, and open the same `ProfileDialog` the popup opens, so nothing below the entry point is duplicated. **Sign-out is separate and always last**, held to the bottom edge by `mt-auto` over a `pt-12` floor — the auto margin alone collapses on a short screen and the two would touch.

`Header.jsx`'s `pageTitles` does carry `/profile` for the desktop title bar; on a phone the header shows the wordmark instead, so it never appears there.

**`/appointments` also drops the header below `sm`**, and for a different reason from `/profile`'s. It is the one page in the app with a *definite* height rather than a minimum — the grid has to fit the viewport exactly — so 68px spent on a bar carrying a wordmark and two icons is 68px the hours do not get. The bottom bar already says which screen this is and still leads to the other four, which is what that header was doing there. Both its page module and its page element subtract 50 rather than 118 below `sm`; the three numbers move together or the page grows a scrollbar. Three pieces, all owned by `Sidebar`:

- `ProfileMenu.jsx` — the popup anchored beside the sidebar's avatar button. It **grows out of its own bottom-left corner** (320ms opening, 130ms closing; opacity + scale + a 6px shift toward the rail). Opening is deliberately the slowest thing in the app and closing is among the quickest: a panel you asked for can afford to unfold, while one you dismissed should already be gone, which is where the button that opened it sits, so the panel reads as coming from the control. `AnimatePresence` for it lives in `Sidebar.jsx`, not here — a component cannot animate its own exit once React has unmounted it. Transforming is safe despite the scrollbar trap on the public shell: this is `position: fixed`, and fixed elements do not contribute to the document's scrollable overflow. Contents: identity header, the section list, then **Sign out** at the bottom (the app's only sign-out control — it calls `/auth/logout` best-effort, then clears local tokens regardless). Section entries are **buttons that open the dialog**, not links. It owns its own dismissal (outside click, Escape); the `data-profile-menu-toggle` attribute on the sidebar button is what stops an outside-click handler from closing and instantly reopening it on the same press.
- `ProfileDialog.jsx` — the modal the sections open into. It fades and scales in (backdrop 200ms, panel 240ms from `scale: 0.97`), so the dim reads as the room going dark and the panel as the thing arriving in it; both **fade rather than slide**, because a centred dialog comes from nowhere in particular and travel would invent a direction that does not exist. Radix keeps its behaviour throughout — `asChild` on `Dialog.Overlay` and `Dialog.Content` hands Motion the element Radix would have rendered, so the focus trap, scroll lock and dismissal are untouched. There's no navigation inside it: switching sections means going back to the popup. `account` (`components/profile/AccountSettings.jsx`) and `security` (`components/profile/SessionsSettings.jsx` — the active-sessions list, with the red "Удаление аккаунта" zone **held to the bottom edge** by `mt-auto` over a `pt-8` floor, exactly as `/profile` holds its sign-out — the empty panel above it is what stops a cursor running down the session list from landing on the one action here that clicking again does not undo. That makes the panel a flex column, which is why every top-level child in it carries `shrink-0`: a flex item defaults to `flex-shrink: 1`, so a long session list would be squashed toward min-content inside the fixed-height panel instead of scrolling) have real content; the rest render `ComingSoon`. **Panel size is per-section**: every section shares one fixed `728×580` box so the window doesn't jump between openings, except `account`, which is a narrow `520px` column that grows downward with its content (a wide box left it stranded in the middle).
- `components/profile/sections.js` — the single `PROFILE_SECTIONS` array both of the above read. **Add a section here and it appears in both**; there's no page to create. `label` is the menu entry; an optional `dialogLabel` overrides the dialog heading when it should read differently (the menu says "Профиль", the heading says "Редактировать профиль").

Two layering details that are easy to break: the avatar cropper is a modal *inside* a modal, so it sits at `z-[70]` above the dialog's `z-[60]`, and it tags itself `data-nested-overlay` — `ProfileDialog` checks for that in `onEscapeKeyDown` and calls `preventDefault()`, otherwise one Escape press closes both. (Outside-clicks need no such guard: the cropper renders inside the dialog's own subtree, so Radix never counts a click on it as outside.) And `AccountSettings` calls `onUserChange` after every save so `DashboardLayout` can refresh the avatar in the sidebar without another `/auth/me` round trip. **Photo changes are staged, not applied immediately** — a crop is held as `{blob, url}` (the object URL being the preview the avatar circle shows) and a removal as an `avatarRemoved` flag; both count toward `isDirty` and only reach `POST`/`DELETE /auth/me/avatar` when Save runs, ahead of the profile PATCH. The staging effect revokes the previous object URL when the crop is replaced.

**Email and password are not inline fields** — each is an `ActionRow` (read-only value + "Изменить") that opens its own step, because neither can be changed by simply saving the form. The email step has two phases (`emailStep`: `'address'` → `'code'`); the password step has two proofs (`pwMode`: `'password'` | `'code'`). Only first/last name and username are part of `FORM_ID` and `isDirty`.
- `Header.jsx` — sticky 68px top bar with **no fill but a hairline under it**: it sits straight on the page's grey ground, the way the bottom bar does, and the rule is what stops the header and the page reading as one flat field — most obvious in dark mode, where no shadow is doing that work either. On a phone it carries the AIRec wordmark instead of the page title — the rail that normally shows the name is not there, and the bottom bar already says which screen you are on, so a title here would say it twice. From `sm` the page title returns, from a `PAGE_TITLE_KEYS` map keyed by route — it holds translation *keys*, not titles, because it is built once at import; update it when adding a new dashboard route. Because it is transparent *and* sticky, it will need the ground colour or a blur behind it as soon as a page can scroll, or content will run under it and show through. On the right sits `HeaderSearch` and then **two icon links, wallet then bell**, both rendered by the local `HeaderLink` so they cannot drift apart. They live here rather than in the sidebar rail because both are things you *check*, not places you work: the four screens in `NAVIGATION` are where the day is spent, these are glanced at and left. That is also why neither is in that array — the bottom bar's five slots are full, and this row shows on a phone too, so both stay reachable without a sixth glyph squeezing the others. The bell carries no unread badge yet, since there's no backend to count.

  **`HeaderSearch` searches nothing yet, and nothing about it pretends otherwise.** There is no index and no endpoint; what exists is the field. It is a real `<input>` rather than a button dressed as one, because a button that does nothing when pressed is a dead control while a field with nowhere to send its text is merely unfinished. **There is no ⌘K badge**, unlike the reference: a badge is a promise about a key, nothing worth opening sits on the other side of that key yet, and binding one silently would be worse — Ctrl+K is the browser's own, and taking it without saying so is a shortcut nobody can find and everybody trips over. It belongs here the day the field opens something. It is `hidden sm:flex`: a 240px pill will not share a 375px row with a wordmark and two icons, and a search that reaches nothing has not earned a screen of its own on a phone.
- `/notifications` — reachable only from that bell. Renders a real empty state ("Пока нет уведомлений") rather than a `ComingSoon` placeholder: a new account genuinely has nothing there, so this is what the finished page looks like too.
- `/wallet` — «Кошелёк», reachable only from the header icon beside it, and built to the same shape so the two read as one pair. **Its empty state is worded in the future tense, and that is the difference from `/notifications`**: a new account really does have no notifications, but a balance of «0 ₸» would be a number nobody computed — there is no payments table, no top-ups and no subscription charges behind it. The page says what will be here rather than pretending it already is.

### Motion
- `PageTransition.jsx` — **every route change in the app, in one place.** Both shells render it in place of `<Outlet/>`, so `/login` ↔ `/signup` and Главная ↔ Записи change the same way: a ~280ms cross-fade, out fast and in a little slower. Four things in it are load-bearing. **`useOutlet()` rather than `<Outlet/>`** — the outlet element has to be captured into a keyed child, or the leaving page renders the *arriving* route's content as it fades; that is the classic React Router + AnimatePresence bug and it reads as a flicker. **`mode="wait"`** so the two never overlap — both shells centre a column, and two stacked read as a double image. **Opacity only, no slide**: every page is exactly one viewport tall (`min-height: calc(100vh - Npx)` under an N-pixel header), and a transform contributes to an ancestor's scrollable overflow even though it does not affect layout, so downward travel puts a scrollbar on screen for the length of every transition — it is also the truer effect, since routes replace each other in place and nothing actually travels. And **`initial={false}`**, so a hard load paints at once instead of fading in. The shells — rail, header, active nav item — stay outside and update instantly; a click should be acknowledged now.

  **`mode="wait"` has one trap worth knowing.** The outgoing page stays mounted for the length of its fade, and by then `useLocation`/`useSearchParams` already report the *next* route. A page that reads a search param **at render time and redirects on its absence** will therefore fire that redirect on its way out, overriding the navigation you just made. `/reset-password` did exactly that — leaving it via any link landed on `/forgot-password`. The fix is to capture the param once in a `useState` initialiser, which runs a single time and survives the re-renders the exit causes. Reading a param inside an effect, or only to decide what to show, is safe.

  Two things to keep if this is extended. **`m` + `LazyMotion features={domAnimation}`, never bare `motion.div`** — the full component carries layout projection, drag, scroll and SVG morphing and so cannot be tree-shaken; the subset costs ~46 kB less. And **motion is not free**: the library adds ~77 kB raw / ~28 kB gzipped to the bundle for this one transition. Second and third uses are cheap; a first use somewhere else should still be worth it on its own.

  **The sidebar's active marker slides.** `Sidebar.jsx` gives the blue square a shared `layoutId="sidebar-active"` instead of putting a background on whichever item is current, so Motion recognises it as one element moving and travels it from the item you left to the one you picked. It rides a spring rather than a duration — the gap between items varies, and a spring handles a long move and a short one in times that both feel right. The icon needs `relative z-10`: an absolutely positioned sibling paints over static content whatever the DOM order, so without it the marker swallows the glyph.

  That marker is why `Sidebar` loads **`domMax` where everything else loads `domAnimation`** — layout projection is the one feature the smaller bundle leaves out, and it costs about 12 kB gzipped. Nothing else in the app needs it; keep new work on `domAnimation` unless it is another shared-element move.

  The profile overlays are documented above: the menu grows out of its own bottom-left corner, the dialog fades and scales in behind a dimming backdrop. Both are `position: fixed`, which is why they may transform where a page may not.

  `/appointments` is where most of the rest of the motion in the app is, and all of it is documented in that section: the four popovers share one `PANEL_MOTION`, the month and the week step *directionally*, the calendar's selection travels on a `layoutId`, and the grid rises over the cards between two definite percentages. Every one of them honours `prefers-reduced-motion` — `useReducedMotion()` where it is a Motion value, `motion-reduce:` where it is a class.

  Motion rules for anything new, from `ui-ux-pro-max`: 150–300ms, ease-out entering and ease-in leaving, `opacity`/`transform` only (never height), **at most one or two moving things per view**, and always honour `prefers-reduced-motion`. Animation that does not answer "what just happened" or "where did this come from" is decoration, and decoration is what makes a screen loud.

### Theming — light and dark

**Colours are semantic tokens now, not raw hexes.** `@theme inline` in `globals.css` maps `--color-*` utilities onto plain custom properties (`--ground`, `--surface`, `--ink`, `--muted`, `--line`, `--line-strong`, `--accent`, `--accent-strong`, `--danger`, `--ok`, `--rail`, `--rail-ink`, `--scrim`), which `:root` sets for light and `[data-theme='dark']` overrides. **`inline` is the load-bearing word**: a plain `@theme` bakes values into the utilities at build time, so `bg-surface` would compile to `#fff` and no runtime switch could reach it.

Use the tokens (`bg-surface`, `text-ink`, `border-line`, `text-muted`, `bg-accent`) in anything new.

**Two of them exist because a fill cannot be one alpha in both themes.** In dark mode `surface` and `ground` are the same black, so a card with no hairline drawn in `surface` is nothing at all — which is why the project's card pattern carries `border border-line`. These are the other way to separate a block from the page:

| Token | Light | Dark | What it is for |
| --- | --- | --- | --- |
| `surface-raised` | `#ffffff` | `#0e0e0e` | a card that carries no edge — the three cards on `/appointments` |
| `surface-chip` | `#ffffff` | `#2a2a2a` | the thing that is *chosen* — a segment, the add button, today in the calendar |
| `surface-card` | `#ffffff` | `#1c1c1c` | a card drawn *on* something rather than on the page — a booking on the timetable's grid |
| `hatch` | `ink / 11%` | `white / 20%` | the stripe over a closed hour on the timetable |

`surface-chip` cannot be an ink alpha for the reason worth remembering: the chosen pill has to be **lighter than its track**, and lighter means *less* ink on the light side and *more* on the dark. Opposite directions from the same value; two literals is what that costs.

**Scrollbars are the app's own**, styled once in `@layer base` for every element: `scrollbar-width`/`scrollbar-color` for Firefox and Chrome 121+, the WebKit pseudo-elements for everything older, and a transparent track — a bar visible with nothing to scroll is a line pretending to be a border, and each of these sits inside a card or a grid that already has edges. The thumb is `--scroll-thumb`, ink at 20% (36% on hover) — **the one surface colour that genuinely wants the same rule in both themes**, since ink at an alpha is a dark grey on a white page and a light grey on a black one. It floats via `border: 3px solid transparent` + `background-clip: content-box`, which is the only way to put padding on a scrollbar.

**Field edges are a `box-shadow`, not a `border`** — `shadow-[0_0_0_1px_var(--color-field)]`, with `field-hover` and `field-focus` steps plus a 4px `field-halo` on focus. The values are measured off `vercel.com/login` (white 14 / 24 / 51% on dark, black 8 / 21 / 34% on light). A shadow sits outside the box model, so focus can thicken the ring without the input growing a pixel and nudging the whole form. **Use `var(--color-field)`, not `var(--field)`** — only the `@theme inline` names are registered, and Tailwind silently drops an arbitrary value referencing an unregistered variable.

**Borders are `line` / `line-strong`, never `muted` at an alpha** — dividers take the first, the edges of inputs and outlined buttons the second. That is not tidiness: grey at 25% reads clearly on white and all but disappears on a near-black ground, so the *colour* has to change with the theme and not only its opacity. Dark uses **one solid grey for both** — `#454545`, from Vercel's `--ds-gray-500`. Two things there. *Solid* rather than white-at-an-alpha: an alpha line is a different colour on every surface it crosses (the page, a card, a dimmed backdrop), where a fixed grey is the same line everywhere. And *one tier*, because on a pure black ground the step down to `#2e2e2e` reads as a second kind of line rather than the same line at a lighter weight, so a header rule and a menu divider stop matching. Light keeps two distinct alphas — there the surfaces are close enough in lightness that the distinction helps and never shows as a mismatch. The header's rule vanishing in dark mode is exactly what this fixed. The old `bg-[#171215]` style still works and is light-only by construction — 281 of them were converted to get here.

Three tokens are **not** flipped roles, and that is the part worth understanding:

- **`rail` / `rail-ink`** — the sidebar is dark in *both* themes. Its colour is an identity, not a role, so it has its own pair rather than following `surface`. **Its active marker is `bg-rail-ink`, not `bg-accent`**: on a light page the accent is black, and a black marker on a near-black rail would disappear.
- **`scrim`** — the wash behind a modal stays dark in both. `ink` at 50% becomes a *light haze* once ink is near-white, which is the opposite of dimming.
- **`accent` is monochrome** — `#000000` on light, `#FFFFFF` on dark. **There is no brand hue in this project any more**: it runs on those two colours, and emphasis comes from contrast and weight rather than from a colour. Anything sitting *on* a solid accent takes `text-surface`, never `text-white` — on the dark side the accent is white and white-on-white vanishes. `danger` and `ok` stay coloured, since those are signals rather than identity.

A `bg-ink` button (the inverted primary on the auth pages) must carry `text-surface`, not `text-white` — in dark mode it becomes a light button, and white text on it would vanish. An accent button keeps `text-white`, since the accent is blue in both.

**State** is in `lib/theme.js`: three choices, `system` (default) / `light` / `dark`, stored in `localStorage` under `airec_theme` with `system` recorded as the *absence* of a key. `applyTheme` writes `data-theme` on `<html>`. The same one line runs as an **inline script in `index.html` before first paint** — set it after hydration and the page renders light then corrects itself, and that flash is worse than no dark mode. The two implementations must agree. `App.jsx` keeps a `prefers-color-scheme` listener so «Системная» tracks the OS while the settings panel — which otherwise owns this — is closed.

The UI is `components/profile/AppearanceSettings.jsx`, rendered for the `settings` section: **two rows of a plain list**, label left, value and chevron right, hairlines between them and nothing around them. It was two cards of three explained options before, which spent half a panel saying what one word already says; a setting with a small closed set of answers is a row, not a section. Adding a third costs one `<SettingRow>`.

**The row is inert and the dropdown is `@radix-ui/react-select`.** A native `<select>` laid over the whole row at zero opacity was here first, and its *behaviour* was perfect — keyboard, typeahead, form semantics, and the system wheel picker on a phone, all for free. What sank it is the part a native select will never hand over: **the list it opens is drawn by the operating system**, a white sheet with a blue bar through it, and this project has no blue and two colours. Radix ships the hard behaviour and no appearance at all, which is the whole reason the styling rules name it as the exception.

That is not a reversal of the `/business` decision. `@radix-ui/react-select` lost there to a `popover` + `cmdk` combobox because eighty-odd cities need filtering and a select has nowhere to put a search box. Three fixed options need none of that, and a select is the primitive.

Three details worth keeping. `Select.Portal` is required — the dialog panel is `overflow-hidden` with rounded corners and would clip the popup. The content is `z-[70]` (above the dialog's `z-[60]`, the avatar cropper's tier) and carries `data-nested-overlay`, so one Escape closes the list and not the dialog behind it. And the trigger takes `-my-4 py-4`, which makes it as tall as the row without making the row taller — a 52px target where the text alone is 20.

And the language rows name each language **in itself, never translated**: someone who switched into a script they cannot read has to be able to find their way back, and «Ағылшынша» is no help to a reader looking for English.

The rows sit under a **named group heading** («Интерфейс»), which is what makes a second group — notifications, say — an addition rather than a redesign. The section keeps the standard `728×580` panel like every other one; a narrower auto-height box was tried and taken back out.

**The rows have no hover state, and that is on purpose.** A full-width tint under the cursor said "this whole line is a button" about a line that is mostly a label — the control is the dropdown on the right, and it is the only thing that reacts. Inside the open list, Radix's `data-[highlighted]` covers pointer *and* arrow keys as one state, which is why the items need no hover rule of their own either.

**Focus is a tint, never a ring** (`focus-visible:bg-ink/6` on the trigger). An outline around a control sitting flush in a list reads as an error state; and while it was a native `<select>` there was a harder reason — Chrome counts a *click* on one as `:focus-visible`, because it opens a listbox, so the outline appeared every single time you used it. A Radix trigger is a real `<button>` and a mouse click leaves no mark, but the tint stays: it is the right look here regardless.

### Styling convention
- Tailwind v4, configured entirely via the `@theme` block in `src/styles/globals.css` — there is no `tailwind.config.js`. It runs through **`@tailwindcss/vite`**, the first-party bundler plugin: there is no `postcss.config.mjs` and no `postcss` dependency, because the plugin replaces that whole chain.
- **Any plain (non-`@layer`) CSS rule in `globals.css` beats every Tailwind utility, regardless of specificity or source order** — `@import 'tailwindcss'` expands to named layers (`theme, base, components, utilities`), and per the cascade-layers spec, unlayered styles always outrank layered ones. `globals.css` learned this the hard way: a bare `button, input, textarea, select { font: inherit }` silently ate every `font-*`/`text-[…]` utility ever applied to a form control, project-wide, until it was moved inside `@layer base`. Any new global reset in this file must go in `@layer base` (or another named layer) or it will do the same thing again.
- Brand tokens: `--color-brand-blue #3248f2` (accent/CTA), `--color-brand-black #171215` (text/dark surfaces), `--color-brand-gray #999999` (borders, typically at 20–45% opacity), `--color-brand-soft #f6f8fa` (page background), `--color-brand-white #ffffff`.
- Components overwhelmingly reference these as raw Tailwind arbitrary values (`bg-[#171215]`, `border-[#999999]/25`) rather than the semantic `bg-brand-*` classes. Match that existing convention instead of switching styles mid-codebase.
- Font: **Onest Variable**, one face for the whole product, loaded as a single `@fontsource-variable/onest/wght.css` import in `src/main.jsx`. `font-display` and `font-sans` both point at it — see **Palette** for why both names stay.
- Each page pairs with a CSS Module in `src/styles/` for its root container — the convention is `min-height: calc(100vh - Npx)` plus a background color, and nothing else. `N` must match the actual current height of that layout's header component (`Header.jsx` or `LandingHeader.jsx`) — check the header's `h-*` class rather than assuming a fixed number, since header heights get tuned independently. All other styling is inline Tailwind utility classes.
- Icons: `@hugeicons/react` + `@hugeicons/core-free-icons` via the `HugeiconsIcon` component — not emoji, not another icon set.
- No UI component library (no shadcn/ui, MUI, Ant Design, etc.). Components are hand-built with Tailwind. **Radix primitives are the one exception, and only for behaviour** — `@radix-ui/react-dialog` backs `ProfileDialog`, `@radix-ui/react-popover` backs everything that opens on `/appointments`, and `@radix-ui/react-select` backs the two dropdowns in «Настройки» and the status row in the booking panel. **Which primitive wins depends on the list, not on taste.** For a *fixed, tiny* set — three themes, three languages — a select is right: jump-to-letter is enough and there is nothing to search. For every closed-set field on `/business` — city, payment methods, languages, times, durations — it is wrong for exactly the reason it was tried and removed there: eighty-odd options need filtering, a select owns every keypress, and there is nowhere inside it for a search box to live. Those went through one `@radix-ui/react-popover` + `cmdk` combobox and will again; cmdk is the piece that supplies the filtering and arrow-key/ARIA wiring. Reach for one when a widget's *behaviour* is hard to get right (focus trapping, keyboard navigation, ARIA wiring: dialog, popover, select, dropdown, tabs), never for its looks. shadcn/ui was considered and deliberately not adopted: it is Radix plus a default Tailwind skin built on `--background`/`--foreground` CSS variables, and this project's design language is fixed and unusual enough that the skin would be discarded — leaving a second token system, a path alias and a TS-first codegen to maintain for nothing. Take a single shadcn source file (its `Calendar`, say) if it saves real work; don't adopt the system.

### Palette — five brand colours, open to more

`design/color_font.png` is the brand, and `@theme` in `globals.css` matches
it. These five are the **base** every screen is built out of:

| Token | Hex | What it is for |
| --- | --- | --- |
| accent | ink / surface | the colour that means *this one* — monochrome, see Theming |
| ink | `#171215` | text, dark surfaces, tooltips |
| muted | `#999999` | borders (at 15–30%), secondary text |
| ground | `#F6F8FA` | the page behind the cards |
| surface | `#FFFFFF` | the cards themselves |

**They are not a ceiling.** Colour may be added wherever it carries meaning the
five cannot: category badges and statuses. `BOOKING_COLORS` in
`lib/appointments.js` was the per-item case — a hue per booking so one could be
told from another at a glance — and it is **no longer used**: a week of coloured
blocks is a week that looks like something is happening, and nothing on that
screen needed a colour to mean anything. The array stays for the day something
does. Two things keep an open palette from turning into noise:

- **A new hue should say something.** Decoration is what makes a screen loud;
  a hue that distinguishes one row from another is doing work.
- **Match the family.** New colours sit in the same saturation and lightness
  band as `#3248F2` so they read as one set rather than as stickers.

`#16A34A` and `#DC2626` keep their meaning — up/down, ok/error — so avoid them
as decorative choices where a reader could take the signal literally. Where they
*are* used, spend them on the few things worth spotting: on `/appointments` only
two of the four booking statuses are coloured, because painting every card makes
colour say nothing.

**Tints are the colour at low alpha** (`bg-[#16A34A]/8`, `bg-[#3248F2]/[0.06]`)
rather than a separate pastel hex, so a tint always tracks the colour it came
from. Filled buttons darken on hover — `#2839C9` and `#B91C1C` — because
lowering alpha would lighten them against white, the wrong direction.

**The typeface is `Onest Variable`, and it is the only one.** It was Poppins
for headings and numbers over Roboto for text — two downloads, four weight
files, and a rule to remember about which numbers belonged in which face. Onest
carries both roles, so the rule is gone along with the way for the two to drift.

`--font-sans` and `--font-display` both resolve to it. **Both names stay**,
because about a hundred elements are written in terms of them and because the
*roles* are still real — `display` is what a heading or a number takes, `sans`
what a sentence takes. Point one of them at something else and the distinction
comes back on its own.

It was chosen over Inter, Manrope and Golos Text for having a geometric voice
close to the Poppins it replaces while being drawn Cyrillic-first. **Geist, the
obvious choice for a design measured off `vercel.com`, is impossible here: it
ships `latin` only.** So does Jost, and `cyrillic` without `cyrillic-ext` is no
better — that is the subset holding **ә ғ қ ң ө ұ ү һ**, which is to say most of
written Kazakh. Check `cyrillic-ext` on the Fontsource API before considering
any replacement.

### Dashboard visual language
**This is the design direction for the product**, taken from `design/main_page.png` — every dashboard screen still to be built (Главная, Диалоги, Записи, Бизнес, Уведомления) starts from it, and existing screens are brought in line as they're touched rather than in a separate pass.

The numbers below are **defaults, not prohibitions**. They exist so that a screen built without a decision still comes out consistent; deviate where the screen is better for it, and where you do, say why in a comment so the next reader knows it was chosen rather than missed.

**Cards.** Page content lives in cards on the `#F6F8FA` page ground:

```
bg-white  rounded-2xl  p-6  →  gap-6 between siblings
```

**Elevation is allowed, in three steps.** White on the grey ground already separates a card, so a shadow is there to give the surface weight, not to hold it up — which is why every step below is wide, soft and low-opacity rather than a dark edge under the box:

```
resting card   shadow-[0_1px_2px_rgba(23,18,21,0.04),0_8px_24px_-12px_rgba(23,18,21,0.10)]
interactive    hover:shadow-[0_2px_4px_rgba(23,18,21,0.05),0_12px_32px_-12px_rgba(23,18,21,0.16)]
floating       shadow-[0_16px_48px_-8px_rgba(23,18,21,0.28)]   dialogs, menus, tooltips
```

Keep the gap between *floating* and the other two: it is the cue that separates "a layer over the page" from "a block on it". A hairline (`ring-1 ring-[#171215]/6`) may accompany a shadow where the card sits on white rather than on the grey ground.

**Prefer a divider to a second card.** Internal grouping reads best as a `1px` line (`border-[#999999]/15`) plus a small muted label; four related KPIs as **one card split by hairlines into a 2×2** is the single most characteristic move of this style, and four separate cards say they are four subjects. Nest a card only when the inner thing really is its own object.

**Card header.** Title at `text-[15px] font-semibold`, optional control on the far right: either a small pill (`rounded-lg border border-[#999999]/25 px-3 py-1.5 text-[13px] text-[#999999]`, e.g. «За неделю ⌄») or a `•••` menu button. Nothing else competes at the top of a card.

**Numbers are the loudest thing on screen.** A metric is three stacked lines: label `text-[14px] text-[#999999]`, value `text-[32px] font-bold tracking-[-0.02em] text-[#171215]`, then a delta line — coloured percentage (`#16A34A` up / `#DC2626` down) followed by muted context («+12% за 28 дней»). Nothing between those lines but tight spacing.

**Charts carry little chrome.** No gridlines, no axis lines, no borders, no legends boxed off. Axis labels are `text-[11px] text-[#999999]`. Sparklines are a bare 2px stroke, green or red, no fill, no dots. Bars are fully rounded pills (radius = half the bar width), `#3248F2` for the one bar being highlighted and `#3248F2` at ~12% for all the rest. An area chart is a soft accent-tinted gradient that bleeds to the card's bottom edge, clipped by the card radius.

**Tables carry no frame.** Column headers are `text-[11px] uppercase tracking-wide text-[#999999]`; rows are separated by air and, at most, a `#999999/15` line — never vertical dividers, never zebra striping, never an outer border. Status is a tinted pill: `bg-[#16A34A]/10 text-[#16A34A]` / `bg-[#DC2626]/10 text-[#DC2626]`, `rounded-md px-2.5 py-1 text-[12px] font-medium`. Amounts right-align.

**Spend the accent sparingly.** In the reference `#3248F2` appears about four times — the active nav item, one highlighted bar, one donut segment, one icon badge — and everything that is data-but-not-the-point wears the lavender tint instead. The count is not a quota; the point is that the accent means *look here*, and a screen where every series is blue has nothing left to point with.

**Icon badges**, where a metric needs one, are `h-7 w-7 rounded-lg` with a solid fill and a white glyph. A hue other than the accent belongs here readily — the badge labels a distinct category, which is exactly the work a colour should be doing.

**Where the app still diverges from the reference**, listed so it is a decision
rather than a drift:

- **The shell is flush; the reference floats.** There, the whole app is a
  rounded container inset on the grey page, with the dark rail rounded on its
  left corners. Ours is a 64px rail hard against the window edge and a 68px
  header. Adopting the frame is structural, so it is not assumed.
- **The header title is 24px, not the reference's ~30.** Our header bar is 68px
  where the reference's is far taller, so the page-title step lands one notch
  down. A breadcrumb was tried there and taken out: with a flat route table the
  trail is always Главная › <page>, and a path that never branches is chrome.
  The search pill **is** built now — see `HeaderSearch` — with two departures
  from the reference. It does not take the reference's `#F6F8FA` fill: our
  header has no fill of its own, so the pill sits straight on the page ground
  and a pill the colour of the ground is a shape nobody can see; it wears
  `bg-surface` and the standard field ring instead, which also gives it an edge
  in dark mode where both are black. And it carries no `⌘K` badge, for the
  reason given above.
- **Cards will need a hairline, not a shadow.** In dark mode `surface` and
  `ground` are both `#000000`, so a border is the only thing that can give a
  card an edge; the reference's resting shadow is invisible there. The pattern
  to use is `rounded-2xl border border-line bg-surface`.

### Mobile

`index.html` sets `maximum-scale=1, user-scalable=no` because pinch-zoom was asked to be off. Two things to know before relying on it: it **fails WCAG 1.4.4**, and **iOS Safari has ignored both flags since iOS 10**, so on an iPhone the line changes nothing.

**Pinch-zoom is refused in two places, because the two engines listen to different halves of it.** `main.jsx` calls `preventDefault` on `gesturestart` with `{ passive: false }` — that is the event an iOS pinch begins with and the one thing Safari does still honour; a listener attached once at startup also cannot be unmounted by a route change or missed by a portal. `globals.css` sets `touch-action: pan-x pan-y` on `html, body` for Chrome and Android, which keeps every scroll in the app and leaves out only the pinch. Both **fail WCAG 1.4.4** and are here because they were asked for.

The zoom people actually hit on iOS is different and is not refused at all — Safari magnifying the page when a text field under `16px` takes focus, never zooming back out. That is fixed where it is caused: **every input in the app is `text-[16px]` up to the `sm:` breakpoint** and drops to 14 above it. It began on `/login` and `/signup`, and the booking panel's seven fields, the phone's search and the profile sheet's three were brought in line once the phone had windows of its own. Any new form field needs the same pair, or the page will jump the first time someone taps it on a phone. `HeaderSearch` is the one input left at 14 and may stay there: it is `hidden sm:flex`, so a phone never sees it.

What replaces the viewport flags for the thing they were meant to fix is `touch-action: manipulation` in `@layer base`, which drops the ~300ms a mobile browser waits after a tap in case a second one means "zoom". It makes taps respond at once and takes nothing away from someone who needs to magnify.

**`/`, `/login` and `/signup` drop the header below `sm`** — `PublicLayout` holds the set, and `LandingHeader` takes a `className` so it is hidden rather than unmounted. On a phone each of those three is a self-contained screen that already offers what the header would: the landing page has both calls to action in its body, the auth pages cross-link at the bottom. A 64px bar repeating them costs a tenth of the viewport. `/forgot-password` and `/reset-password` keep it, deliberately — they are mid-flow, and the header is the way back out.

The three page modules pay for that with a media query: `min-height: 100vh` below `sm`, `calc(100vh - 64px)` above it, matching the breakpoint the header returns at. They are also `display: flex; flex-direction: column`, and their content centres with **`m-auto`, not `justify-center`** — `justify-center` clips the top of anything taller than the viewport instead of letting it scroll, which the signup form is on a short screen.

Touch targets on the auth pages and the landing header grow on small screens (`py-3 sm:py-2`) to clear the 44px minimum; the 68px/64px headers and the 400px auth column already fit a 375px screen, so nothing else needed a breakpoint. `-webkit-text-size-adjust: 100%` stops iOS resizing text on rotation.

### UI language — three, switchable; Russian is the source
**The frontend speaks Russian, Kazakh and English**, chosen in the profile's «Настройки» section and remembered in `localStorage` under `airec_lang`. **Russian is the source language and the fallback**, not English: the product is sold in Kazakhstan, where a business owner reads Russian whichever language they prefer, so a key missing from `kk` or `en` falls through to something they can still act on. Write new copy in `ru` first, then the other two.

Everything lives in `src/lib/i18n.js` plus one file per language under `src/lib/locales/`. There is **no React context and no i18n library** — the language is a module-level variable with a `Set` of listeners, because it is read at every depth in the tree and threading a provider through all of it would be a lot of plumbing for one string.

The API is small and worth knowing whole:

- `useT()` → the `translate` function, plus a re-render when the language changes. **This is what a component uses.**
- `translate(key, vars, lang)` → the same thing without the subscription, for code that is not a component (`lib/api.js`'s network errors) or that runs in a callback rather than a render (`AvatarCropper`'s `img.onerror`). It reads the language at *call* time, which is exactly right there and is also why it must not go in a `useEffect` dependency list.
- `useLanguage()` → `[lang, setLanguage]`, for the settings panel.
- `getLocale()` → the BCP 47 tag (`ru-RU` / `kk-KZ` / `en-GB`) for `toLocaleDateString` and friends. **Dates are part of the translation** — `SessionsSettings.formatMoment` takes its locale from here rather than being pinned to `ru-RU`, or a Kazakh screen would show Russian month names.
- `vars` fills `{name}` placeholders (`'Отправить снова ({seconds} с)'`), which is what keeps a sentence one translatable string instead of fragments a translator has to reassemble in an order their language may not use.

**A missing key renders as the key itself** (`login.title`), deliberately: that is a gap you can find on screen, where an empty string is a bug you cannot.

Two rules that are easy to break:

- **A module-level constant may not hold a translated string.** `NAVIGATION`, `PROFILE_SECTIONS`, `SECTION_PLACEHOLDERS` and `Header`'s `PAGE_TITLE_KEYS` are all evaluated once at import, so a translated label there would freeze in whichever language happened to load first and never follow a change. They hold **keys** — `labelKey`, `dialogLabelKey` — and the components call `t()` at render. The same goes for a translated default in a function signature: `AvatarCropper`'s `title` has no default, and falls back to `t('cropper.title')` in the JSX instead.
- **Nothing keeps the three dictionaries in step but you.** They are plain objects with no schema; the check is one command:

  ```
  node --input-type=module -e "import ru from './src/lib/locales/ru.js';import kk from './src/lib/locales/kk.js';import en from './src/lib/locales/en.js';const r=Object.keys(ru);console.log(r.filter(k=>!(k in kk)),r.filter(k=>!(k in en)))"
  ```

`applyLanguage()` runs from `App.jsx` and stamps `<html lang>`, which is what a screen reader picks its voice from; `index.html` sets it a second time before first paint. Unlike the theme that pre-paint copy is **not** load-bearing — nothing is painted from `lang`, and the store has already read `localStorage` by the time React's first render happens, so there is no flash to prevent. It is there because getting the attribute right before the document is announced costs one line.

**The backend answers in the caller's language too.** `lib/api.js` sends `Accept-Language: <lang>` on every request, read at call time so it follows a language change made while the tab is open, and `app/core/i18n.py` picks the wording. It translates only the two failures it generates itself (`timeout`, `network_error`) plus the last-resort unknown — everything else arrives already worded. See **Messages the API returns** below for how the backend side works and what is still Russian.

**`src/lib/cities.js`, `appointments.js`, `businessOptions.js` and `schedule.js` are still untranslated** — about 150 Russian strings between them. `cities.js` and `businessOptions.js` belong to `/business`, which is still empty, and are tree-shaken out of the build; translate them when that screen comes back.

The other two are now in use, and the split matters. **Where a translated string was needed, the component was given keys rather than the lib being translated** — `StatusFilter` reads `booking.active` / `booking.completed` / `booking.noShow` / `booking.cancelled` instead of `BOOKING_STATES[].label`, because a filter whose options are in a language the rest of the panel is not in looks broken. `BOOKING_STATES`' own Russian labels stay where they are for code that has no `t` to call; `formatDuration` and `formatPrice` still produce Russian units («30 мин», «5 000 ₸») on every screen, which is the largest untranslated surface left in the app.

`dates.js` is the one that has started. It now holds **two kinds of label and the split is the point**: the hand-written `MONTHS` / `DAY_LETTERS` tables stay Russian and predate the UI speaking three languages, while anything a reader sees goes through `Intl` keyed on `getLocale()` — `monthLabel()` and `weekdayLabels()`, both **functions rather than constants**, because a module constant would freeze in whichever language loaded first. Follow that pattern for the rest of the module rather than writing three tables by hand: `formatToParts` is what avoids Russian's trailing " г.", and the month part is capitalised on its own rather than the string's first character, since Kazakh puts the year first and raising position zero would capitalise a digit.

Making the backend fully Russian took two non-obvious pieces, both in play for any new field you add:

- **Pydantic's own validation messages are English and can't be localised in place.** Where the text matters, the constraint is enforced by a `field_validator` raising a Russian `ValueError` instead of by `Field(min_length=...)` — that's why `Password` is a plain `str` with `validate_password_length` / `validate_new_password` attached, rather than an annotated constrained type. For the few built-ins a client can still trigger, `app/main.py` keeps a `_PYDANTIC_MESSAGES_RU` map keyed by Pydantic's error `type`.
- **`EmailStr` reports through `value_error`, the same type our own validators use**, so it can't be told apart by type — `_field_message` matches it on the message text prefix instead and swaps in "Некорректный email."

Ruff's `RUF001`-`RUF003` ("ambiguous unicode character") are disabled in `pyproject.toml` for this reason: Cyrillic that resembles Latin is the whole point here, not a typo.

## Backend architecture (`backend/`)

FastAPI + SQLAlchemy 2.0 async + asyncpg + PostgreSQL 18, migrated with Alembic. See `backend/README.md` for the endpoint table and setup steps.

### Layering — keep the direction of dependency
`app/api` (HTTP) → `app/services` (rules) → `app/repositories` (queries) → `app/models`. Services raise `AppError` subclasses from `app/core/errors.py` and must never import FastAPI or raise `HTTPException`; `app/main.py` owns the mapping from error to response. Repositories own all query construction — don't write `select()` inside a service or route.

Every failure leaves the API in one envelope, `{"error": {"code", "message"}}` (422 adds a `fields` array), so the frontend needs only one parser. Preserve that shape when adding endpoints.

### Auth model — the non-obvious parts
- **Argon2id runs on a worker thread** (`anyio.to_thread` in `app/core/security.py`). Hashing inline in an `async def` would stall the event loop for every concurrent request — keep any new password work on that path.
- **Login always performs a verification, even with no matching user**, against a module-level dummy hash. That's deliberate: it stops response timing from revealing which accounts exist. Don't "optimise" the early return away.
- **«Запомнить меня» is two halves, and neither works alone.** `POST /auth/login` (and `/auth/restore`, the same schema) takes `remember`, which picks the refresh token's lifetime — `refresh_token_ttl_days` (30) against `refresh_token_session_ttl_hours` (12) — while the client picks the store it keeps the token in: `localStorage` when remembered, `sessionStorage` when not. Doing only the client half leaves a credential live on the server for a month that nobody holds, showing up in «Активные сессии» as a device that has not existed since Tuesday; doing only the server half leaves the token on a shared machine's disk. The flag lives on `refresh_tokens.remember` and is **carried across rotation exactly like `family_id`** — otherwise it would last one refresh, and a session the user asked not to remember would promote itself to thirty days the first time its 15-minute access token expired. `change_password` reads it off the caller's live token *before* revoking everything, for the same reason. `_issue_tokens` takes it as a **keyword with no default**, so each of the five places that mint a pair states its own answer rather than inheriting one silently — registration says `True` (an account is made on its owner's own machine), a password change inherits, a refresh carries.

  Two defaults that deliberately disagree: the **schema** defaults `remember` to `False`, so a client that forgets the field fails safe toward a session that ends too early; the **login form** ticks the box, because AIRec is a panel its owner opens every morning and defaulting to off would sign them out every night and read as a bug. `signup.jsx` has no checkbox at all — the one case where it would matter, registering on a borrowed computer, is answered by signing out. And `sessionStorage` is per-tab, so an unremembered session asks for the password again in a second tab; that is what the choice describes, and the other reason the box starts ticked.
- **Access token is a stateless 15-min JWT; the refresh token is opaque and stored only as a SHA-256 digest.** The digest is what makes logout/revocation real. Refresh tokens rotate on every use, and replaying an already-rotated token is treated as theft — it revokes every session for that user.
- **Rotation has to survive a client sending the same token twice, and getting that wrong is not a small bug.** It can happen easily: two tabs share one `localStorage`, and one page can start two session checks at once (`<StrictMode>` double-invokes effects; `useRequireAuth` re-runs on every route change). Both halves of the refresh path had to be hardened, and they fail in different ways:
  - **Both requests read the token as live.** They then both minted a replacement in the same family, leaving one session with two live `refresh_tokens` rows — the same device listed twice in «Активные сессии», both labelled "Текущий", identical in every visible column. `RefreshTokenRepository.revoke` is now a conditional `UPDATE … WHERE id = :id AND revoked_at IS NULL` returning whether it won: under READ COMMITTED the second statement blocks on the row lock, re-evaluates its `WHERE` after the first commits, and matches nothing. `uq_refresh_tokens_live_family` — a partial unique index on `family_id WHERE revoked_at IS NULL`, migration `0018` — makes "one live token per session" a database rule rather than a convention any future code path could quietly break.
  - **The second request reads the token *after* the first committed**, so it sees a revoked row and is indistinguishable from a replay by inspection. This is the more common outcome, and it was the worse one: the theft response fired and killed every session the user had, including the replacement the first request had just issued — so a double-click signed you out. `refresh_token_reuse_grace_seconds` (default 10) is the fix, and it is **two** tests, not one: the token must have been revoked within the window **and** its family must still hold a live token. A token whose family is empty was ended deliberately — a logout, a previous theft response — so anything arriving with it is a replay whenever it turns up. Inside the grace the loser gets a plain 401 and *nothing is revoked*; outside it, or with a dead family, the full response still fires.

  The client side matters too, and `lib/auth.js` carries both halves: `verifySession()` is **single-flight** (concurrent callers share one in-flight promise, so a tab never sends the same token twice), and a failed refresh re-reads storage before giving up — if another tab rotated the token meanwhile, it retries once with the new one instead of clearing tokens and signing both tabs out.
- **Sessions are token families, not rows.** Because rotation revokes the token it replaces, a signed-in device has exactly one live `refresh_tokens` row at any moment — which is why `GET /auth/me/sessions` is a plain `revoked_at IS NULL AND expires_at > now()` query rather than a grouping. What survives rotation is `family_id`, carried onto every replacement together with `user_agent`, `ip_address` and `first_seen_at` (and the invariant is enforced by `uq_refresh_tokens_live_family`, not assumed); `created_at` therefore means "last refresh" and is what the UI shows as last activity. The access token carries the family as a `sid` claim, which is how the listing marks the caller's own row without a client ever sending its refresh token to a read endpoint (`sid` is optional when decoding — tokens minted before this existed simply lose the marker). `app/core/useragent.py` turns the stored header into a label like "Chrome, Windows"; it is a handful of substring checks on purpose, since the only job is helping someone recognise their own device. Device details are read in the route and handed to the service as a plain `ClientInfo` dataclass, keeping FastAPI out of the service layer.
- **Identity casing:** emails are normalised to lowercase in the schema layer and get a plain unique index; usernames keep their typed casing but are unique case-insensitively through a `lower(username)` unique index, which also backs the login lookup. `AuthService._conflict_for` matches on the constraint names `uq_users_email` / `uq_users_username_lower` — rename either index and that mapping breaks silently.
- **Live username check:** `GET /auth/username-availability?username=` (public, no auth) backs the signup form's real-time green-tick/red-warning UI. `AuthService.check_username_available` treats a malformed username as unavailable without hitting the database — it never has to distinguish "invalid" from "taken" for the caller, both just render as "not available" (see `signup.jsx`).
- Registration pre-checks duplicates for a precise message, but the unique indexes are the actual guarantee; a race surfaces as `IntegrityError` and is mapped back to the same 409.
- **Password policy is charset + length, checked on registration only.** `Password` (shared by register/login) enforces 8–128 chars; `RegisterRequest` additionally runs `_validate_password_charset` against `PASSWORD_CHARSET_PATTERN` in `app/schemas/auth.py` — Latin letters, digits, and a fixed symbol set, no whitespace or other scripts. Login doesn't re-check the charset since a stored password was, by construction, already valid at registration time. `app/main.py`'s `_field_message` strips the "Value error, " prefix Pydantic v2 glues onto `raise ValueError(...)` messages from field validators — write new validator messages assuming that prefix is gone. `signup.jsx` mirrors the rule as a static hint under the password field, swapped for the live `422` message on failure; `login.jsx` doesn't need either since it's just entering an existing password.

### Account deletion is a grace period, not a delete
`POST /auth/me/delete` sets `users.deleted_at` and revokes every refresh token; **nothing is removed** until `account_deletion_grace_days` (default 30) has passed. `deleted_at` is deliberately separate from `is_active` — one is the user's own reversible decision and carries a deadline in its message (`AccountDeleted`, with the date), the other is an administrator switching an account off. Authentication, refresh, *and* `get_current_user` all reject a deleted account, the last of those because the access token that performed the deletion stays cryptographically valid for its remaining minutes.

**The proof is the current password plus typing the username — no emailed-code alternative.** Reusing `password_reset_codes` here would mean a code issued to change a password could also delete the account, which is not a trade worth making. The confirmation string is compared case-insensitively.

`POST /auth/restore` {identifier, password} clears `deleted_at` and signs the user back in; `login.jsx` offers it automatically when a sign-in fails with code `account_deleted`, since the credentials were already accepted. Restoring an account that isn't deleted just signs in normally.

**The purge is what actually deletes**, and it runs from `app/main.py`'s lifespan at startup — this project has no scheduler, so that is what makes the 30 days real. It only removes rows whose `deleted_at` is past the cutoff, cascades to tokens and codes, and deletes avatar files **after** the commit (a restored account should come back with its picture). Point a cron at `AuthService.purge_deleted_accounts` when there's somewhere to run one. Note the consequence of soft deletion: **the email and username stay taken for the whole grace period**, which the deletion UI says out loud.

### Password reset flow
`POST /auth/forgot-password` {email} → **deliberately the one enumeration-unsafe endpoint in this API**: unlike login, it raises `EmailNotRegistered` (404) when the address isn't registered instead of pretending to succeed — a conscious trade of that leak for a clearer frontend error message. If the user exists, it invalidates any prior unused code (`PasswordResetRepository.invalidate_all_for_user`) and issues a new one via `generate_reset_code()` — a `secrets.randbelow`-sourced 6-digit string, stored only as a SHA-256 digest on `PasswordResetCode`, expiring after `password_reset_code_ttl_minutes` (default 10).

`POST /auth/reset-password` {email, code, new_password} verifies against the user's *latest* unused code — scoped by `user_id` before comparing hashes, deliberately, because a 6-digit code only has ~1M possibilities and a global (cross-user) hash lookup risks a coincidental collision. A wrong code increments `PasswordResetCode.attempts`; at `password_reset_max_attempts` (default 5) the code is dead even if the *correct* one is subsequently tried — this attempt counter, not the hash, is what actually protects a code this short-entropy from brute force, since there's no rate-limiting middleware in this project to lean on instead. On success it revokes every refresh token for that user (`RefreshTokenRepository.revoke_all_for_user`), the same "something was wrong, kill all sessions" move as replayed-refresh-token theft-response.

**Email delivery has a dev-mode fallback by design.** `app/core/email.py` sends via `smtplib` (blocking, so it runs through `anyio.to_thread` like Argon2 and refresh-token hashing) only when `settings.smtp_host` is set. With no SMTP configured — the default in `.env.example` — it logs the code as a `WARNING` to the server console instead and returns; this is what makes the flow testable locally without a mail account. Fill in `SMTP_HOST`/`SMTP_USER`/`SMTP_PASSWORD`/etc. in `.env` to actually send mail.

**Changing a password from inside a session takes either of two proofs, never both.** `POST /auth/me/password-change/confirm` accepts `{new_password, current_password}` *or* `{new_password, code}` — a `model_validator` on `ChangePasswordRequest` rejects sending neither or both, so the service never has to guess which branch it's in. Neither proof dominates: the password path survives losing the mailbox, the code path survives the password having leaked, and both require more than a live session. The UI defaults to the password path (no email round trip) with a "Не помните пароль?" link that calls `POST /auth/me/password-change` (auth required, no body) to mail a code and switch modes. Both go through `password_reset_codes` rather than a third near-identical table, because both flows authorise exactly the same thing — "set a new password for this user" — so the latest code winning across both is the behaviour you want. `AuthService._consume_reset_code` is the shared validator (expiry, attempt ceiling, digest compare, attempt increment); `reset_password` and `change_password` differ only in what they do afterwards. The confirm endpoint **revokes every refresh token including the caller's own and returns a fresh `TokenPair`** — that's what logs out other devices without logging out the device doing the change, and `AccountSettings` must `saveTokens()` the response or the next request 401s.

`ResetPasswordRequest.new_password` reuses `validate_password_charset` (the standalone function `RegisterRequest` also uses) rather than duplicating the charset check — if the password policy changes, both call sites move together.

### Profile and avatars
`PATCH /auth/me` is a true partial update: `UpdateProfileRequest` has every field optional and the service reads it with `model_dump(exclude_unset=True)`, which is what separates *"field omitted → leave it alone"* from *"field sent as null → clear it"*. Changing `username` to a different casing of the same name must not 409 against the user's own row — `AuthService.update_profile` compares lower-cased before running the uniqueness check.

**Changing the email is a separate, verified flow — `PATCH /auth/me` has no `email` field at all.** Accepting it there would let a client set an address it doesn't own. Instead `POST /auth/me/email-change` {new_email} emails a 6-digit code **to the new address** (receiving it is the proof of ownership) and stores a pending `EmailChangeCode` row — `users.email` is untouched until `POST /auth/me/email-change/confirm` {code} succeeds. The code table mirrors `PasswordResetCode` (SHA-256 digest, TTL, `attempts` counter as the real brute-force defence, latest-unused-per-user lookup scoped by `user_id`), and confirmation **re-checks that the address is still free** — it may have been registered by someone else while the code sat unused. `app/core/email.py`'s `_code_email_html` is shared by both flows; only the heading and lead line differ. `GET /auth/me/email-change` reports the address still awaiting confirmation (null once it expired or ran out of attempts, so the UI never offers a "confirm" that cannot succeed) — that's what lets `AccountSettings` show a persistent **Не подтверждён** banner with a Подтвердить button after the dialog is closed and reopened. `DELETE /auth/me/email-change` abandons it (idempotent, and the abandoned code stops working immediately) — without that the banner would sit there until the code expired, with no way to take back a mistyped address.

**`users.email_verified_at` is what "confirmed" actually means** — set only by `confirm_email_change`, exposed as the computed `User.email_verified` in `UserPublic`. **Registration never verifies**, so every account starts unverified and migration `0007` deliberately backfills nothing. That's also why `request_email_change` accepts the account's *own current* address when it is still unverified (and only then raises `SameEmail`): sending a code to the address you already have is how an existing account proves it. `confirm_email_change` skips the "already registered" re-check in that case, since `email_exists` would match the user's own row. The status strip under the Email field reads from this: pending change → red with the new address, unverified → red with a Подтвердить that sends the code, otherwise green **Подтверждён**.

**Names are stored split** — `User.first_name` / `User.last_name` (50 chars each). `full_name` is a **computed property** joining the two, not a column, so there's no stale joined copy to keep in sync; it's still in `UserPublic` for callers that just want a display name. Migration `0005` split the old `full_name` column (first word → `first_name`, remainder → `last_name`). `AccountSettings.jsx` edits the two parts and reads `user.full_name` only for the identity strip.

Uploaded images live on local disk (`backend/uploads/`, gitignored) and are served by `StaticFiles` mounts. `app/core/images.py` owns all of it: an `ImageStore` is just a directory plus a URL prefix, and there are two — `AVATAR_STORE` and `LOGO_STORE`. **They're kept apart deliberately**: an avatar dies with its user and a logo with its business, so mixing them would make a cleanup pass over either one dangerous. The DB column holds the **filename only**; `User.avatar_url` and `Business.logo_url` are computed properties that prepend the prefix, so storage can move without a data migration. Every upload is re-decoded and re-encoded through Pillow rather than stored as sent — that's what rejects non-images and strips EXIF or any payload hidden in a valid-looking file, and it runs on a worker thread for the same reason Argon2 does. Old files are deleted only *after* the new row commits, so a failed write never orphans the existing image.

### The business behind an account
`Business` (`app/models/business.py`) is where everything the assistant sells hangs off — services, hours and bookings will belong to it, not to `users`, because a business will eventually have more than one person attached. One per account for now: `owner_id` is **unique**, and `BusinessRepository` deliberately exposes no `get_by_id` — every read is scoped by owner, so no endpoint is one refactor away from serving one account's data to another.

**The price list and the week are saved whole, not row by row.** `PUT /business/services` takes the entire list: an item with an `id` is updated in place, one without is created, and anything the list omits is deleted — all in one transaction. That matches how the card is edited (fix three prices, rename one service, then press Save once) and means the list can never be left half-applied. Matching on id rather than rebuilding the table is what keeps a service's identity — and, later, its bookings — across an edit; an id belonging to another account simply doesn't match, since the lookup is scoped to this business, so it is created as new instead of touching a foreign row. The frontend tags locally-added rows with a `new-…` id, which `serviceToApi` converts to `null`.

`working_hours` is always **seven rows** — a missing row and a closed day have to read differently, so `GET` creates the week on first access (Mon–Sat 10:00–20:00, Sunday closed; a guess meant to be corrected, but a better starting point than an assistant that can never book). `weekday` is `0 = Monday`, matching Python's `datetime.weekday()` and the frontend's `WEEKDAYS` array, so no translation table exists to get out of step. Times are `time` columns, not text, and are serialised back as `"HH:MM"`. A break sent on a closed day is dropped rather than stored, or it would reappear the moment the day was reopened.

**Round the clock is `is_24h`, a boolean — not `00:00–00:00` and not `00:00–23:59`.** Both encodings are guesses a reader has to decode, and the second silently loses a minute a day that a slot generator would then have to forgive. The flag leaves `opens_at`/`closes_at` **null**, and `replace_working_hours` clears them (and the break — nothing can interrupt a day that never closes) whenever it is set, so the two can never be read disagreeing with each other. `WorkingHours.is_open` returns true for such a day. It is marked **per day**, from a «24 ч» chip sitting between the day name and its opening time — a whole-week pill in the card header was tried and removed; the per-day mark is the primitive, and "24/7" is just all seven of them set. The chip stays visible while off (muted, 12px) rather than appearing on hover: it's the only place in the product that offers a round-the-clock day, so a hover-only affordance would leave the feature undiscoverable.

**A day must be readable as opening hours before it can be saved.** `WorkingHoursInput`'s `_coherent_day` model validator refuses a closing time at or before the opening one, an opening without a closing (or vice versa), a half-specified break, and a break that falls outside the working day. It sits on the schema rather than in the service because every rule compares two fields of the same row. **A close before an open is rejected, not read as running past midnight** — the two columns can't express "the next day", so interpreting it would turn a typo into a twenty-two-hour day; an all-night business sets `is_24h` instead. That is a real limitation for a bar open 18:00–02:00, and the fix is an explicit overnight flag, not a silent wrap. `frontend/src/lib/schedule.js`'s `dayProblem` mirrors the same rules — not out of distrust, but because a 422 arriving after Save names a weekday *number*, while the owner is looking at a row. Keep it a single function when the schedule UI is rebuilt: two copies agree only until one is edited.

**Every time in this product sits on a 15-minute grid**, enforced in `app/schemas/service.py` (`SLOT_MINUTES`) on all four working-hours times *and* on `duration_minutes`. Booking is fitting durations into gaps between hours, and that arithmetic only stays exact while both sides share one unit — a 40-minute service against a 10:05 opening leaves offcuts nothing else can fill. The validator is on the schema, not trusted to the pickers, since the pickers aren't the only possible client; it drops seconds rather than rejecting them (`"10:00:00"` plainly means ten o'clock). The UI has to offer the same step: a quarter-hour list is 96 entries long, which is why the time pickers were searchable and why the combobox seeded its highlighted value on open — otherwise the menu opens at 00:00 with the current value far below the fold.

**It's created lazily, on first `GET /business`, not at registration.** Signing up shouldn't decide anything about the company, and this way an account that never opens the page carries no half-filled row — while every other endpoint can still assume a business exists instead of carrying a "not set up yet" branch. `timezone` is the one column with a default (`Asia/Almaty`) and the one `PATCH` refuses to null: a time stored without knowing its zone can't be repaired afterwards, and that has to be true *before* the first booking exists.

### Bookings
`Appointment` (`app/models/appointment.py`) is what the whole product produces. Five statuses (`pending` → the assistant's own output, then `confirmed` / `completed` / `cancelled` / `no_show`), and **only `cancelled` gives the time back** — `BLOCKING_STATUSES`. A no-show still happened *to that slot*; treating it as free would let the past be double-booked the moment anyone looked at it.

**Archiving is a third thing again, and it is a *view* flag.** `PATCH {"archived": true}` stamps `appointments.archived_at`; listings by date drop archived rows, but the search (`?query=` alone) keeps them, since a booking put out of the way is exactly the kind you go looking for by name. Crucially `list_blocking` passes `include_archived=True`: archiving must never hand an occupied hour back out, or availability would depend on housekeeping. A timestamp rather than a boolean because "when was this put away" is free and `NULL` is the only value that can mean "never was".

**Cancelling and deleting are different acts.** Cancelling is a status (`PATCH {"status": "cancelled"}`) and keeps the row — it is what the owner looks back on to see how often bookings fall through, and the assistant needs to know it already spoke to this client about this time. `DELETE /appointments/{id}` removes the row outright, for one that should never have existed (a typo, a duplicate, a test): nothing fell through, so there is nothing to look back on, and leaving it as a cancellation would put a client in the history who was never booked. **`DELETE` used to cancel**, which made the verb say one thing and do another; the frontend helper was renamed `cancelAppointment` → `deleteAppointment` at the same time, so an old caller fails to build rather than quietly deleting what it meant to cancel.

**A booking does not have to come from the price list.** `CreateAppointmentRequest.service_id` is **optional**: given, it names and prices the booking; omitted, `service_name` and `price` carry it and the row simply has no service to point at — which the column already allows, since a deleted service leaves exactly that. All three of `service_name`, `price` and `duration_minutes` are also accepted *alongside* a `service_id`, and override it field by field. A model validator makes the three of them required together when there is no service, because a booking missing any one is a row that cannot be shown in a calendar or counted in a total.

Why: the price list is what a business usually sells, and a day contains what it sells once — a one-off job, a favour, an amount agreed on the phone, a visit that ran long. Refusing those would make the calendar a record of the price list instead of a record of the day.

**Appointment times are no longer on the 15-minute grid.** `SLOT_MINUTES` still governs everything a *client* is offered — working hours, breaks, and the starts `available_slots` generates — because that is the arithmetic of fitting durations into gaps, and it stays exact only while both sides share one unit. A booking the owner writes down is not that: it is a record of when somebody actually sat down, which is 14:07 as often as it is 14:00, and rounding it to keep a generator tidy would be filing the day wrong to make the maths pretty. Overlap checks are range comparisons and do not care.

**`capacity` constrains clients, not the owner** — the same way `min_lead_minutes` and `booking_horizon_days` do, and through the same `source` test. It exists so the assistant cannot promise an hour that is already spoken for, and defaults to 1 because an assistant that cannot tell a full hour from an empty one has to assume the cautious answer. None of that describes the owner writing a booking down: two people at half past is an ordinary afternoon, and a panel that refuses to record it is a calendar arguing with the day it is meant to be a record of. A `manual` booking therefore skips `_ensure_room`, on create *and* on reschedule — a booking written by hand does not become subject to capacity because it was later moved. **Opening hours stay outside that flag**, as they always were.

**The service is both a foreign key and a copy.** `service_id` is `ON DELETE SET NULL`, and `service_name` / `duration_minutes` / `price` are snapshotted at booking time and never refreshed *by an edit to the price list*. The price list is edited constantly; without the snapshot, correcting one price would silently rewrite what every past booking cost. The key links a booking to a living service, the copy is what the booking *was*. `PATCH /appointments/{id}` may send a new `service_id` — a client asking for something different on arrival has changed the same booking, not made another one — and that path re-snapshots all three fields together, since a `service_id` sitting beside yesterday's name and price is a row disagreeing with itself. Because it can change the booking's length it counts as a move: `ends_at` is recomputed and opening hours and capacity are re-checked exactly as for a new `starts_at`. `ends_at` is likewise derived but stored, because every availability check is a range overlap and computing the end in SQL would rule out an index — `AppointmentService` is the only writer, so the two can't drift.

**The PATCH says everything a POST can, which took two changes in the service.** `service_name`, `price` and `duration_minutes` are accepted on their own and applied *after* the service block, so an explicit value overrides whatever the price list just supplied and a booking with no service can still be renamed or repriced — and a new `duration_minutes` counts as a move exactly as a new `starts_at` does. And `service_id` is read with `"service_id" in changes` rather than `is not None`, because `null` is a *value* here: it unhooks a booking from the price list, which is what happens when the owner types over the service's name, and `exclude_unset` is what keeps that distinct from not sending the field at all.

**A booking may carry a colour, and the column holds a name.** Migration `0019` adds nullable `appointments.color`; `BOOKING_COLORS` in `app/schemas/appointment.py` is the closed set the server will accept (`orange green blue violet rose teal`) and `null` is the ordinary case. A **name and not a hex**, for two reasons that both matter: what a name looks like is the frontend's business, which is the only way a mark can differ between the light theme and the dark one, and the only way the palette can be retuned without an `UPDATE` over every row ever written. It has been retuned twice already — six muddy mid-tones for six Tailwind 500s, then those for a set constructed at one OKLCH lightness — and not one stored row changed either time.

**All booking arithmetic happens in `app/services/appointment.py`, in absolute time, via `Window` tuples.** Opening times are wall-clock and can't express either half of the two things that actually matter: a break splits a day into two stretches, and midnight joins two days into one. `_windows_around` therefore builds the day *before*, the day, and the day *after*, then `_merge` joins any that touch — which is what lets a 23:45 booking run into a round-the-clock following day instead of being refused because the calendar changed date halfway through it. `available_slots` applies hours, breaks, existing bookings, `capacity`, `min_lead_minutes` and `booking_horizon_days` in one place; a caller that re-derived any of them would be a second implementation of the rules.

**`tzdata` is a hard requirement, not a nicety.** Windows ships no IANA database, so `zoneinfo` has nothing to read and every slot calculation raises `ZoneInfoNotFoundError`. It's pinned in `requirements.txt` for that reason, and `UpdateBusinessRequest` now validates `timezone` by constructing a `ZoneInfo` — an unknown name would otherwise only surface deep inside slot generation, reading as a broken calendar rather than a bad setting.

**Booking is read-then-write, so it takes a row lock.** `BusinessRepository.lock` does `SELECT … FOR UPDATE` on the business row before counting what occupies a time; without it two requests for the last place would both read "room for one" and both insert. Serialising per business costs nothing while bookings arrive seconds apart.

Where a booking sits is re-checked only when it has been *chosen* again (create, or a `starts_at` that actually moved) — marking a two-week-old booking as `completed` must not fail because its time is long past `min_lead_minutes`. Capacity, separately, is re-checked whenever the booking starts occupying something it wasn't: a new time, or a cancellation being taken back.

**`min_lead_minutes` defaults to `0` — there is no advance-notice rule unless a business asks for one.** "Can I come now?" is an ordinary question for a barbershop, and a client who walks in without ever opening WhatsApp still has to be written down. The column stays (migration `0015` only changed the default and zeroed the rows that carried the old hour), so notice can be switched back on per business without a migration.

**Notice, horizon and opening hours constrain clients, not the business** — `_ensure_within_rules` *and* `available_slots` both take an `enforce_notice` flag, and `source` is what decides it. **The two must agree**: `GET /appointments/slots?source=` defaults to `manual` exactly as `POST /appointments` does, because a picker that hides times the create call would accept is a picker that lies — that mismatch is what made the panel refuse to offer 12:00 at 11:33 while the endpoint behind it would have taken it. With the flag off the whole day is offered, this morning included. A `manual` booking (the owner, from the panel) skips `min_lead_minutes` and `booking_horizon_days`: writing down someone who walked in twenty minutes ago is recording something that already happened, and refusing it would be refusing reality. A `whatsapp` booking gets both. Rescheduling always skips them, because every PATCH currently comes from the panel — when the assistant gets its own way in, it will have to say so. **Opening hours used to sit outside that flag and no longer do** (the parameter is `enforce_client_rules` now, not `enforce_notice`). The old argument was that they catch a mistyped date for the owner too, and that was wrong about what the owner is doing: a booking written by hand is a record of something agreed or already done — somebody came during the break, somebody was fitted in after closing — and a calendar that refuses to write those down is arguing with the day it exists to record. The mistyped date is answered where it belongs, in the panel, **as a warning before Save rather than a refusal after it** — `hoursProblem` in `lib/schedule.js` reports `off` / `break` / `shut` for the chosen span and `BookingPopover` says so in `--now` orange, which does not block saving. Red would claim something failed when nothing has. For the assistant nothing changed and nothing may: "book me while you're closed" is not something a client can be told yes to.

`GET /appointments?query=` searches client name **and phone, ignoring punctuation** — `_matches_client` strips non-digits from both the stored number and the query, so "7701", "701 555" and "+77015553322" all find a client saved as "+7 701 555 33 22". A query with no digits never touches the phone column. A search with no `from`/`to` drops the date range entirely rather than defaulting to the next thirty days: looking for a client means looking for every visit they ever made.

### The inbox — conversations and messages

`Conversation` + `Message` (`app/models/conversation.py`, `message.py`) are what `/inbox` will read. **Backend only so far: nothing on the frontend touches any of this yet.**

**The rule the whole thing exists for: a person from the business writes, and the assistant goes quiet in that thread.** `ConversationService.add_message` sets `assistant_enabled = False` whenever the author is `owner`, and it lives in the service rather than in the route so it holds however the message got made. It stays off until somebody switches it back on (`PATCH {"assistant_enabled": true}`) — not until the end of the day and not on a timer, because whoever stepped in once is usually handling that client now, and a bot resuming on a clock resumes in the middle of somebody else's sentence. The assistant's own messages leave the flag alone, for the obvious reason that otherwise it could answer exactly once.

**`MessageAuthor` is one column, not a direction plus a sender.** `client` / `assistant` / `owner`: direction is implied (the client is the only one on the other end) and the distinction that actually matters — assistant versus owner — is the one a direction column would throw away.

**Three statuses, and two things that deliberately are not statuses.** `new` (nobody has answered, the assistant included) → `open` → `closed`, where only `closed` is set by hand. *Live right now* and *waiting on us* are **derived**, never stored: a stored "active" needs something to switch it off again and nothing ever would, so a thread marked active at two o'clock is still marked active at midnight. Live is a window over `last_message_at` (`conversation_active_minutes`, default 15) applied in the service, since the window's length is a setting; waiting is `last_message_author == client`, exposed as the computed `awaiting_reply` and available as a filter through an `EXISTS` that keeps an empty thread out of both answers.

**The last message is copied onto the conversation row** — `last_message_at`, `last_message_author`, `last_message_preview` (160 chars, cut on whitespace). Same trade as `appointments.ends_at`: the list screen is "every thread, newest first, with a line of preview", and getting that out of SQL is a lateral join or a window function on every read. `_remember_last` is the single writer, called from all three places that can change what the newest message is — including `delete_message`, which rebuilds it, or deleting the newest one would leave the list showing a line that exists nowhere.

**Archiving, starring and deleting are three different acts**, following the calendar's precedent exactly. `archived_at` and `starred_at` are timestamps rather than booleans (NULL is the only value that can mean "never was", and a starred list can be ordered by when each was starred); the API takes them as booleans and the service does the translation. Archived threads are dropped from the list by default and `archived=null` includes both. `DELETE` removes the row and cascades to the messages — for a wrong number or a test, not for something dealt with.

**`ingest` is the one entrance for anything inbound.** It finds the thread or opens one, learns the provider's `external_id` the first time it appears, bumps `unread_count`, reopens a `closed` thread (somebody writing again is the definition of not being finished), and **drops a redelivery on the floor** — a webhook is redelivered on any doubt, so `messages.external_id` is unique per conversation and a second copy returns the first. Finding the thread tries the provider id first and falls back to the phone number *only for a thread with no `external_id` yet*, which is what stops an owner-opened conversation being duplicated the moment the client replies.

**`POST /conversations/{id}/messages` records; it does not send.** There is no outbound transport — WhatsApp means the Business API, a registered number and approved templates, none of which exist — and `POST /conversations/ingest` is authenticated as the owner, which is not where a real webhook ends up either (Meta sends a signature and no bearer token). Both are shaped so the real versions wrap `ConversationService` rather than growing a second copy of the rules.

`unread_count` is cleared by opening the thread (`POST /conversations/{id}/read`), never by the assistant answering — an answered thread is exactly the one the owner still wants to know about. `GET /conversations/unread-count` counts *threads*, not messages, and is declared before `/{conversation_id}` because FastAPI matches in order.

Search (`?query=`) covers the client's name, their number ignoring punctuation — the calendar's rule — **and the text of any message in the thread**, which the calendar has no equivalent of: half of what you remember about a conversation is a word from inside it, and a client may never have given a name at all.

**Still missing:** the WhatsApp webhook and its signature check, any outbound transport, delivery receipts, media messages, and a way to push a new message to an open page (there is no SSE or WebSocket anywhere in this project).

### Messages the API returns
**Russian is the source language and it lives in the code**, exactly as on the frontend. An `AppError` carries its Russian `message`, a `field_validator` raises Russian prose, and both read where they are written. `app/core/i18n.py` holds `kk` and `en` **keyed by the Russian string** — Russian is deliberately absent, because it is what a missed lookup returns, and listing it would be the same text in two places free to disagree.

Keying a catalogue by its source text is what gettext does and it inherits gettext's failure mode: **edit the Russian and its translations stop matching, silently.** So the check is a command, not a habit:

```
cd backend && PYTHONPATH=. .venv/Scripts/python.exe -m app.core.i18n
```

It reads the messages **out of the code** — every `AppError.message`, every string raised by a validator, every value in `_PYDANTIC_MESSAGES_RU`, every literal handed to `translate` — so the inventory cannot drift from reality the way a hand-written list would. It also verifies that a `{placeholder}` present in the Russian survives into both translations, and reports translations whose source string no longer exists. Exit code is non-zero when anything is wrong. 65 messages at the time of writing.

Three things worth knowing:

- **The language is negotiated per request, never stored.** `negotiate()` parses `Accept-Language`, sorts by `q` (header order breaks ties, so `kk,en` prefers Kazakh), and takes the first primary subtag it recognises; anything unparseable falls back to Russian rather than raising, because a malformed header is not a reason to fail a request that is otherwise fine. Both exception handlers in `app/main.py` call it — they are the only place a message becomes a response, so they are the only place that needs it.
- **A message with a value in it is a `str.format` template, and the value travels separately.** `AppError.__init__` takes `**params` and holds them until render time: `AccountDeleted("Аккаунт удалён. Восстановить можно до {date}.", date=…)`. An f-string at the raise site would bake the Russian in and leave nothing to translate.
- **Field errors needed no codes.** The 422 `fields` array carries `field` and `message` and no machine-readable code — a client-side code→message map was the other option here and would have meant inventing one for every validator, keeping it stable, and mapping it again on the client. Translating where the message is written is less machinery and keeps the rule and its wording together.

**Still Russian: the emails.** `app/core/email.py` words the password-reset and email-change messages, and nothing there is translated — a Kazakh reader gets a Russian email. It is a different problem from the ones above: an email is composed in the service layer, which has no request to read a header from, so the language would have to be threaded down as a parameter. Not done.

### Config and migrations
`app/core/config.py` is the only place that reads the environment — import `settings` rather than touching `os.environ`. It rejects a `SECRET_KEY` under 32 chars at startup, by design. `alembic/env.py` takes its URL from those same settings, so there is no second copy in `alembic.ini`. `Base.metadata` uses an explicit naming convention (`app/db/base.py`) — new models inherit it, which is what keeps autogenerated migrations stable. Add every new model to `app/models/__init__.py` or autogenerate won't see it.

PostgreSQL is a native install (`C:\Program Files\PostgreSQL\18`) running as the machine-wide `postgresql-x64-18` service on its own data directory. The app connects as the `postgres` superuser to a database named `airec`; there is no separate application role.
